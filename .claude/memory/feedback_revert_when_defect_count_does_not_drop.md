# 🚨 결함 수가 안 줄면 **되돌린다**

> 개발책임자 (2026-08-07)
> *"결함 수가 같거나 늘면 다시 되돌려서 PM이 분석하고 이를 바로 LUNA를 통해 fix진행 및 검증.
> 그 후 다음 라운드에 넘어가는 것으로."*

## 규칙

라운드마다 **도달 결함 수**를 센다. 직전 라운드와 비교해서:

```text
줄었다        → 그대로 다음 라운드로 (기존 흐름)
같거나 늘었다  → ① 🚨 **되돌리기 전에 PM 이 분석한다**  ← 순서가 중요하다 (2026-08-07)
                     왜 안 들었나 · fix 가 무엇을 깨뜨렸나 · 축이 틀렸나 범위가 좁았나
                     🔑 **되돌리면 그 증거가 사라진다.** diff·재현·원인이 다 없어진다
                 ② **"되돌리면 결함이 몇 개가 되나" 를 센다**
                     늘어난다   → 되돌리지 않는다. **그 수치를 PR 에 적는다**
                     줄거나 같다 → **되돌린다** (fix 직전 커밋 기준)
                 ③ ①의 분석으로 LUNA 가 다시 고친다
                 ④ 검증까지 끝낸 뒤에야 다음 라운드로
```

> 2026-08-07 개발책임자: *"되돌리기 전에 분석은 먼저 하는거 맞지?
> 그래야 어떤 식으로 fix 해야 결함이 없어지는지 알 수 있잖아."*

⚠️ 이 문서의 초판은 *"PM 이 **되돌린 상태에서** 분석한다"* 였다. **순서가 반대였다.**
   되돌린 뒤에는 무엇이 왜 깨졌는지 볼 수 없어, 같은 실수를 반복하는 fix 를 다시 낸다.

🔑 **fix 위에 fix 를 쌓지 않는다.** 안 듣는 fix 를 남긴 채 다음 라운드를 열면
그 fix 가 만든 표면까지 다음 검증이 떠안는다.

## 🆕 2026-08-07 — 되돌림이 **측정상 손해**인 경우 (개발책임자 승인)

되돌림의 목적은 *"안 듣는 fix 를 치우는 것"* 이다. 그런데 실측해 보면
**fix 가 안 들어서 같은 수** 인 경우와 **fix 가 덜 쓸어서 같은 수** 인 경우가 있고,
후자는 되돌리면 **결함이 폭증**한다.

| 실측 | 되돌렸을 때 |
|---|---|
| `#1107` S5→S7→S9 **1→1→1** | 정상 동작 중인 **216파일이 다시 깨짐** (결함 4 → 220) |
| `#1097` S8→S10 **2→3** | HEAD 의 견적 필터 수정까지 사라짐 (F1 은 코드 회귀가 아니라 **배포본 불일치**였다) |

그래서 **되돌리기 전에 세는 절차**를 넣는다.

```text
0  🚨 **먼저 분석한다** — 되돌리면 증거가 사라진다
     fix diff 를 읽고 "무엇이 왜 안 들었나 / 무엇을 깨뜨렸나" 를 확정한다
     ⚠️ UTF-16 등으로 git diff 가 안 보이는 파일은 **변환해서** 읽는다
        (#1119 실측: operational-validation.ps1 이 UTF-16 이라 binary 취급 →
         diff·grep 둘 다 못 봤고, python 변환으로만 회귀를 확인했다)
1  "이 fix 를 되돌리면 도달 결함이 몇 개가 되나" 를 **수치로** 센다
2  늘어나면 되돌리지 않고 **그 수치를 PR 에 적는다**
     예) "되돌리면 4 → 220. 되돌리지 않고 축을 바꿔 재 fix 한다"
3  줄거나 같으면 되돌린다 (`git diff <fix직전> -- <경로>` 가 0줄임을 확인)
4  🚨 0 의 분석으로 재 fix 한다 — 분석 없이 다시 고치면 같은 실수를 반복한다
```

⚠️ **이 예외는 "판단해서 안 되돌려도 된다" 가 아니다.** 수치를 세지 않고 넘어가면 위반이다.
   PM 이 오늘 세 번 되돌리지 않았고 근거는 맞았지만, **규칙에 없는 판단을 즉석에서 했다.**

🔑 같은 수가 **세 번 연속**이면(`#1107` S5·S7·S9) 되돌림 여부와 별개로
   **fix 의 축이 틀린 것**이다. → [[feedback_throughput_parallel_scope_freeze_batch]] R3
   실제로 `#1107` 은 *목록 → 발견 기반* 으로 축을 바꾼 S10 에서야 닫혔다.

## Why — 쌓기가 라운드를 폭증시킨 실측

`#1051`/PR `#1082` 가 이 규칙 없이 굴러간 결과:

```text
R6  라이브QA  → revision UI stale            결함 1
R7  fix       → 저장 1회에 GET 2회            결함 1 (같음 — 여기서 되돌렸어야)
R8  라이브QA  → 복원 후 초안 stale             결함 1
R9  fix       → 다른 세션 미저장 초안 삭제      결함 1 (데이터 손실로 악화)
R10 fix       → 비공유 snapshot 이 Y.Doc 분기  결함 3 (증가)
S11 판정      → D1·D3 미종결
⟹ 다섯 라운드 · 커밋 17개 · 결국 프런트 전체를 분리해 내야 했다
```

**R7 시점에 되돌렸으면 R8~R11 이 없었다.**

같은 날 `#1102`/PR `#1103` 도 같은 모양이었다:
```text
S2 적대검증  → 조회 중 미확정 단가 노출        결함 1
S3 fix       → "빈 값으로 표시"
S4 재검증    → 결함 0 (단위 테스트 근거)
R1 라이브QA  → 여전히 노출 (빈 값이 아니라 `0` + note)   결함 1 (같음 → 되돌림 대상)
```
🔑 **단위 테스트가 0 을 냈어도 라이브에서 같은 결함이 나오면 "같음" 이다.**
   세는 기준은 **도달 결함**이지 테스트 결과가 아니다.

## How to apply

```text
1  라운드 종료 시 PM 이 결함 수를 적는다 (PR 코멘트에 `직전 N → 이번 M`)
2  M >= N 이면 🚨 **되돌리기 전에 먼저 분석한다**
     fix diff 를 읽고 "왜 안 들었나 / 무엇을 깨뜨렸나 / 축이 틀렸나 범위가 좁았나" 를 확정
     ⚠️ UTF-16 등 git diff 가 안 보이는 파일은 변환해서 읽는다
     🔑 되돌린 뒤에는 이 증거가 없다. 순서를 바꾸면 같은 실수를 반복한다
3  "되돌리면 결함이 몇 개가 되나" 를 수치로 센다
     늘어난다   → 되돌리지 않고 그 수치를 PR 에 적는다
     줄거나 같다 → 되돌린다
       되돌림은 정확해야 한다 — **fix 직전 커밋 기준**으로 복원하고
       `git diff <직전커밋> -- <경로>` 가 0줄임을 확인한다
       🚫 `git checkout origin/main -- <경로>` 로 하지 마라 — 다른 PR 산물까지 끌어온다(실측)
       🚫 **검증 이력(보고서·QA 캡처)은 되돌리지 않는다**
4  2 의 분석으로 LUNA 가 고치고 **검증까지** 한다
5  검증이 끝나야 다음 라운드(적대검증·라이브QA)로 간다
```

⚠️ **되돌림은 실패가 아니라 절차다.** 되돌렸다고 라운드를 낭비한 것이 아니라,
쌓았을 때 생길 라운드를 미리 없앤 것이다.

## 세는 법 — 무엇을 결함 1건으로 보나

```text
✅ 센다      실 사용자 경로로 재현 가능한 것 (게이트 ① 기준 그대로)
🚫 안 센다   검증 품질(테스트 약함·mock 미비·문서 과장) · 커버리지 · 네이밍
📌 같은 증상이 다른 형태로 남으면 **같은 1건**이다
   (예: "카탈로그 값 노출" → fix → "0 으로 노출" = 여전히 1건, 해소 아님)
```
