# 🚨 하네스 설계 정본 (2026-07-23)

> 개발책임자: *"결함의 증가여부에 따라 PM이 규칙을 변경해도 될 것 같아. 기본은 지금 규칙으로 하되, 계속 순증하고 역효과라면 예전 규칙대로 해도 좋아. **어쨌든 가장 궁극적인 목적은 결함을 0으로 만드는 것**이기 때문이야. **해당 기능이 쓸모있는가에 대한 질문도 중요**하긴해. PM이 가장 효율적인 하네스를 제시 바라."*
> 개발책임자: *"3턴은 그냥 권고로 하고 PM의 제안을 모두 수용."*

**궁극 목적 = 결함 0.** 라운드 수·속도는 그 수단이지 목적이 아니다.

---

## 0. 설계 목표를 숫자로 — **수렴비 c < 0.45**

지표는 **둘**이다. 하나는 판정용(애매함 없음), 하나는 진단용.

| 지표 | 정의 | 용도 |
|---|---|---|
| **수렴비 `c`** | **이번 라운드 도달가능 건수 ÷ 직전 라운드 도달가능 건수** | **판정** — 적응 규칙은 이 값으로만 움직인다. 귀속 논쟁이 없다 |
| **fix-유발률 `r`** | 이번 라운드 `[NEW]` 도달가능 중 **직전 fix 가 만든 것** ÷ 이번 라운드 도달가능 건수 | **진단** — c 가 높을 때 원인이 fix 인지 리뷰 심화인지 가른다 |

미해결 N 건이 3라운드 안에 1건 미만이 되려면:
```
N · c³ < 1        N=10 ⟹ c < 0.46
```
이 레포 실측은 **c ≥ 1**(#907 이 4건 → 10건으로 늘었다). **그 값이면 라운드를 아무리 돌려도 수렴하지 않는다.**
⟹ 하네스의 유일한 설계 목표는 **라운드를 늘리는 것이 아니라 c 를 0.45 아래로 떨어뜨리는 것**이다. 나머지는 전부 부차적이다.

⚠️ **c 가 1을 넘어도 곧바로 실패가 아니다.** 리뷰 브리프를 도달성으로 좁히면 같은 비용으로 더 깊이 파므로 **일시적으로 발견이 는다**(#907 실측 4→10). 그때는 `r` 을 보고 가른다 — **r 이 낮으면 리뷰가 깊어진 것(정상)**, **r 이 높으면 fix 가 결함을 낳는 것(개입 필요)**.

**매 라운드 c 와 r 을 계산해 PR 코멘트에 기록한다.** 기록하지 않으면 적응 규칙이 작동하지 않는다.

## 2. 하네스 5부

### ① 기획 — **PM 진단 확증 의무**
불변식을 쓰기 전에 **원인을 실행으로 확증**한다. 코드 읽기 추정으로 쓰지 않는다.
확증하지 못하면 **"원인 미확정"** 이라고 적고 구명을 구현자에게 맡긴다. 🚫 추정을 단정으로 쓰지 말 것 — 원인 ④ 차단.

### ② 리뷰 — **5차원 고정 폐기, 표면 분할 3~4 에이전트**
차원(역할)이 아니라 **표면(파일군)** 으로 나눈다. 각 에이전트에게 주는 질문은 **도달성 단일 질문** 하나뿐.
- 실측 근거: #914 5차원에서 도달가능 5건이 나왔는데 **A-1·A-2 가 3~4개 차원에서 중복 발견**됐다. 중복은 비용이다. #907 마감 라운드는 **3차원으로 10건**을 찾았다.
- **도달성 판정 + 종합 + 라이브QA 는 루트**가 맡는다(도달성 = 라이브QA 그 자체).

### ③ fix — 🔴 **최소 변경 원칙** (가장 강한 레버)
> **불변식을 만족시키는 최소 변경만 한다. "온 김에" 금지.**

부피가 곧 다음 라운드 감사면이므로(원인 ③), 구현자는 **변경 줄 수를 보고**하고 늘어난 이유를 설명한다. #914 의 정규식 확장이 정확히 이 규칙에 걸렸을 변경이다.

### ④ fix — **회귀 울타리 + 계열 전수 sweep**
- **회귀 울타리**: fix 지시마다 **"이것은 계속 보여야/동작해야 한다"** 목록을 함께 준다 — 원인 ① 차단.
- **계열 전수 sweep**: 한 곳을 고치면 **같은 패턴이 있는 곳 전부**를 grep 으로 확인하고 목록을 보고한다. 보고 단위는 "고친 곳"이 아니라 **"같은 패턴이 있는 곳 전부"** — 원인 ② 차단. → [[feedback_defect_family_sweep_fix]]

### ⑤ 🚨 **효용 게이트 (U-gate)** — *"기능이 쓸모있는가"*
도달성 축은 *"코드가 사용자에게 거짓말하는가"* 는 잡지만 *"기능이 실제로 쓸모 있는가"* 는 못 잡는다. 적대 라운드에 넣으면 범위가 다시 터지므로 **양 끝에만** 둔다.
- **기획 시 1문장** — *"이 슬라이스가 끝나면 사용자가 **실데이터로** 무엇을 할 수 있게 되는가"* + 구체 시나리오 1개
- **머지 직전 PM 라이브QA 1회** — 그 시나리오를 **실데이터로 실행**. 실행하지 못하면 **왜 못 하는지 명시하고 개발책임자 판단**을 받는다(조용히 머지 금지).

🚩 실증 — **#907**: 실 DB 주문 **2,020건 전부 `partner_id IS NULL`** 이라 legacy fail-closed 결정상 **머지돼도 병합을 실행할 수 없다.** 도달성 축만으로는 도달가능 0 으로 수렴해 **조용히 머지된다.** U-gate 가 정확히 이 지점을 잡는다.

## 3. 적응 규칙 — 언제 무엇으로 바꾸는가

**PM 이 r 을 보고 하네스를 바꿀 권한을 위임받았다.**

| 상태 (2라운드 연속) | 조치 |
|---|---|
| **c < 0.45** | 현행 유지 |
| **c ≥ 0.45 이고 r 이 낮다** | 유지 — 리뷰가 깊어진 것이지 fix 가 낳은 게 아니다. 발견이 소진되면 c 는 내려간다 |
| **c ≥ 0.45 이고 r ≥ 0.5** | 🔧 **fix 분할 동결** — 한 턴에 **뿌리 1개만** fix 한다. 턴 수는 늘지만 표면이 작아 c·r 이 함께 떨어진다 |
| **c ≥ 1 이 3라운드 연속** | PM 이 원인을 규명해 **개발책임자께 보고 후** 규칙 변경 |

### 🚫 "예전 규칙 복귀"는 fallback 이 아니다
개발책임자가 *"역효과면 예전 규칙대로 해도 좋다"* 고 허용했으나, **실측상 예전 규칙(전 심각도 0 + 검증품질 이월)이 더 나빴다** — 검증품질이 도달가능의 **2~9배**로 나와 PM 판정·게시·이월 결정을 전부 소모했고 **밤새 3트랙 머지 0** 이었다.
🔑 **r 이 안 떨어지는 원인은 리뷰 범위가 아니라 fix 부피다.** 되돌리면 노이즈만 돌아오고 r 은 그대로다. 그래서 fallback 을 **fix 분할 동결**로 잡는다.

## 4. 3턴은 **권고**다 (2026-07-23 개발책임자 하향)

1턴 = `OPUS 라운드 + CODEX 라운드`(각 fix 포함). **재수렴까지 3턴을 지향하되 절대 규칙은 아니다.**
- 넘겨도 임의로 끌지 말고 **남은 도달가능 목록 + 각각의 흡수 난이도 + PM 권고**를 개발책임자께 올려 판단을 받는다.
- 3턴을 못 지키는 것 자체는 위반이 아니다. **r 을 기록하지 않고 원인 없이 라운드를 반복하는 것**이 위반이다.
- 참고 고정비(2026-07-23 실측): OPUS 표면분할 병렬 11~20분 · mock 게이트 11분 · CI 15분 · 라이브QA 3~6분 · fix 수십 분 ⟹ **1턴 ≈ 2~4시간**. 3트랙 병렬 시 6~12시간에 3슬라이스가 산술 상한.
