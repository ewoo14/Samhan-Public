# 08-실시간-협업 / 03. 수정 횟수 카운트 (Stage 4)

> ✅ **구현 상태** — Phase 12 step-2 (PR-H2) audit overlay 의 부속 기능으로 완성. PR-H4c 부터 슬립/거래처/재고/세금계산서/배차/사용자 등 audit 적용 모든 항목에 동일 노출.
>
> **본 docs 는 무엇인가요?** — 항목 헤더 우측 상단에 표시되는 **수정 N회** badge 의 의미와 색상 임계 (5회 / 10회) 의 운영 가치를 안내합니다.

- **MASTER / MANAGER** — 비정상적 다수 수정 항목 검토 (감사)

## 1. badge 표시

### 1-1. 위치

항목(슬립/거래처/재고/세금계산서/배차 등) 상세 화면 헤더 우측 상단.

```
[슬립번호] 2026-05-09-001       [상태: 승인대기]   수정 5회
```

### 1-2. 색상 임계

| 횟수 | 색상 | 의미 |
| ---: | --- | --- |
| 0회 | (badge 숨김) | 신규 작성 후 수정 없음 |
| 1~4회 | 회색 | 정상 범위 |
| 5~9회 | 노랑 | 다중 수정 — 주의 환기 |
| 10회+ | 빨강 | 비정상적 다수 수정 — 검토 권장 |

> 0회는 의도적 hide. 신규 작성 직후 화면이 깔끔하도록 설계.

---

## 2. 카운트 규칙

### 2-1. 1 카운트 = 1 [저장] 클릭

한 번의 [저장] 으로 5개 필드를 동시에 변경했다 하더라도 **수정 횟수는 +1** 입니다. (필드 카운트가 아닌 저장 트랜잭션 카운트.)

### 2-2. 자동 status 전이는 카운트 제외

슬립이 SENT → ACCEPTED → PROCESSING 으로 자동 전이되는 경우 **카운트 제외**. 운영자의 명시적 [저장] 만 카운트.

| 동작 | 카운트? |
| --- | --- |
| 운영자 필드 수정 후 [저장] | ✅ +1 |
| status 전이 (`accept` / `process` / `inspect` / `complete`) | ❌ 제외 |
| 시스템 자동 채움 (snapshot — 거래처 전화/주소) | ❌ 제외 |
| 복원 (revision rollback) | ✅ +1 (새 revision 누적) |
| 잠금 unlock 후 수정 | ✅ +1 |
| 수정 요청 / 수락 / 거절 자체 | ❌ 제외 (audit log 만 누적) |
| 인쇄 / 조회 | ❌ 제외 |

### 2-3. 동시 다발 저장 시

한 항목을 두 명이 동시에 저장하면 각각 +1 → 총 +2. (409 CONFLICT 로 한 명이 실패한 경우는 +1 만.)

## 3. badge 클릭 동작

### 3-1. badge 클릭 시 — 전체 audit log 표 노출

수정 N회 badge 클릭 → 별도 모달 / 패널로 항목 전체 audit log 가 표 형태로 노출됩니다.

```
+──────────────────────────────────────────────────────────────────+
│  슬립 #2026-05-09-001 — 전체 수정 이력 (5회)                       │
+──────────────────────────────────────────────────────────────────+
│  rev # │ 시각              │ 수정자 │ 변경 필드          │ 복원   │
+────────┼───────────────────┼────────┼────────────────────┼────────┤
│  5     │ 2026-05-09 16:48  │ 박관리 │ 메모               │  ▾     │
│  4     │ 2026-05-09 14:35  │ 김영업 │ 배송지, 검수지     │  ▾     │
│  3     │ 2026-05-09 14:32  │ 김영업 │ 메모, 결제조건     │  ▾     │
│  2     │ 2026-05-09 11:15  │ 이작성 │ 품목 수량 (3 → 5)  │  ▾     │
│  1     │ 2026-05-09 11:05  │ 이작성 │ (신규 작성)        │  -     │
+────────┴───────────────────┴────────┴────────────────────┴────────┘
│  [ 닫기 ]                                                          │
+──────────────────────────────────────────────────────────────────+
```

| 컬럼 | 의미 |
| --- | --- |
| rev # | 가장 최근부터 1까지 역순 번호 |
| 시각 | 정확한 일시 (오늘 이전은 `MM-DD HH:mm`) |
| 수정자 | 풀네임 (UUID 비공개) |
| 변경 필드 | 변경된 필드 한국어 라벨 (콤마 구분) |
| 복원 | MASTER/MANAGER 만 ▾ 표시 ([04. 수정 복원](04-수정-복원.md)) |

### 3-2. 필드별 inline overlay 와 차이

| 항목 | 필드 inline overlay | badge 클릭 모달 |
| --- | --- | --- |
| 표시 위치 | 본문 필드 옆 | 별도 모달 / 패널 |
| 표시 단위 | 필드별 (`메모` 옆에는 `메모` 변경만) | 전체 항목 (모든 필드 통합) |
| 다중 revision | 펼치기 / 접기 | 표 형태 일괄 표시 |
| 복원 ▾ | 권한자만 표시 | 권한자만 표시 |
| 사용 시나리오 | "이 필드 누가 바꿨지?" 확인 | "이 슬립 전체 수정 흐름 확인" 감사 / 검토 |

## 4. 색상 임계 운영 가치

### 4-1. 5회 (노랑) — 주의 환기

5~9회 수정된 항목은 정상 범위에서 약간 벗어나기 시작한 상태입니다. 다음과 같은 경우가 흔합니다.

- 거래처 요청이 자주 바뀌는 슬립
- 견적 단계에서 단가/품목을 다양하게 시도
- 신입 운영자가 필드 의미를 익히면서 시행착오

> 5회 이상은 운영 차단 사유는 아니지만, MANAGER 가 우연히 발견 시 한번 검토 권장.

### 4-2. 10회+ (빨강) — 비정상적 다수 수정

10회 이상 수정된 항목은:

- 시스템 / 운영 절차 점검 필요 (왜 자꾸 바꾸나?)
- 외부 사기 / 임의 변경 가능성 검토 (audit log 사용자 분포 확인)
- 거래처와의 의사소통 점검 (잦은 변경 요청 = 거래처 confirm 절차 누락 가능)

> 10회 이상 빨강 badge 항목은 MASTER 가 주기적 (월 1회) 검토 권장. catalog 통계 후속 추가 검토.

### 4-3. catalog 통계 (참고)

slip-service 운영 데이터 기준 (PR-H2 머지 후 1주):

| 횟수 분포 | 비율 |
| --- | --- |
| 0회 | ~62% |
| 1~4회 | ~33% |
| 5~9회 | ~4% |
| 10회+ | ~1% |

> 10회 이상은 통계상 매우 드뭄. 빨강 badge 가 보이면 한번 들여다볼 가치 있음.

## 5. FAQ

| 증상 | 원인 | 해결 |
| --- | --- | --- |
| 신규 작성한 슬립인데 badge 가 보임 | 작성자가 작성 후 한 번 더 [저장] 누름 | 정상 — 각 [저장] 마다 +1 |
| 0회인데 badge 가 회색으로 보임 | 캐시 깨짐 | `Ctrl + F5` |
| status 전이도 카운트 되었으면 좋겠음 | 정책 결정 — 자동 전이는 카운트 제외 | 후속 정책 변경은 메모리 가드 추가 후 검토 |
| badge 클릭이 안 됨 | 권한 부족 (audit log 조회 권한 = MANAGER+) | MANAGER 에게 요청 |
| 5회인데 노랑이 아니고 회색 | 5회 정확히 = 노랑 시작 (4회까지 회색) | 정상 — 임계 = 5회 inclusive |
| 빨강 badge 항목을 일괄 조회 | catalog 통계 화면 후속 PR 예정 | 현재는 audit-service 가 monthly report 생성 (Phase 13 후보) |
| 색상이 단색 (회색만) | 사용자 layout 모드 (고대비) | 시스템 설정 → 일반 layout 으로 변경 |
