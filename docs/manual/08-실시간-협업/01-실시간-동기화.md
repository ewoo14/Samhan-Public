## 1. 시각적 동작

### 1-1. 두 운영자, 같은 슬립 동시 작업

영업1팀의 김영업과 영업2팀의 박영업이 같은 슬립 `2026-05-09-001` 을 동시에 열어둔 상황:

![두 컨텍스트 동시 작업 split](https://github.com/ewoo14/SamhanLogis/raw/04e2b44/docs/qa/phase-12-step-1-websocket-infra/working-multi-context-split.png)

좌측 김영업이 메모를 `긴급 출고 요청 (오늘 마감 전)` 으로 변경하고 [저장] → 1초 이내 우측 박영업 화면 메모 필드가 자동 갱신됩니다.

### 1-2. 토스트 + audit overlay 동시 노출

수신 측(우측 박영업) 화면에는 두 가지가 동시에 나타납니다.

1. **우측 상단 토스트** — `김영업이 슬립 #2026-05-09-001 메모 수정` (3초 후 자동 사라짐)
2. **메모 필드 audit overlay** — 새 값 + 취소선 옛 값 + 색상 dot + 풀네임

![수신측 audit overlay](https://github.com/ewoo14/SamhanLogis/raw/732e105/docs/qa/phase-12-step-2-slip-audit-overlay/working-audit-overlay-context-b-receives.png)

## 2. SSE 채널 — 운영자 관점

### 2-1. 동기화되는 이벤트 종류

(주)삼한공조시스템 운영 환경에서 실시간 동기화되는 이벤트는 다음 5종류로 분류됩니다.

| 이벤트 카테고리 | 발생 시점 | 수신자 | 토스트 메시지 예시 |
| --- | --- | --- | --- |
| **항목 수정** (`*.updated`) | 다른 사람이 같은 항목 저장 | 같은 항목을 열어둔 모든 사용자 | `김영업이 슬립 #001 메모 수정` |
| **status 전이** (`*.transitioned`) | 슬립/배차/검수 status 가 다음 단계로 진행 | 동일 항목을 보고 있는 모든 사용자 | `슬립 #001 — 발송 → 접수 (창고 박창고)` |
| **수정 요청** (`edit.requested`) | 본인이 잠긴 항목 수정 요청 보낼 때 | 권한자(MANAGER+/MASTER) | `김영업이 슬립 #001 수정 요청 (사유: ...)` |
| **수락/거절** (`edit.accepted` / `edit.rejected`) | 권한자가 수정 요청 수락/거절 | 요청자 | `수정 요청이 수락되었습니다 (24시간 내 수정 가능)` / `거절되었습니다. 사유: ...` |
| **삭제 알림** (`delete.accepted`) | 항목 soft delete 시 | 같은 항목을 보고 있던 모든 사용자 | `슬립 #001 이 삭제되었습니다. 관련 분개는 회계팀에 통보됨` |

### 2-3. 동기화 지연 시간

| 환경 | 정상 지연 | 트러블슈팅 임계 |
| --- | --- | --- |
| 사내 LAN (gateway 직결) | < 500ms | > 2초 |
| 외부 (인터넷 / 모바일 4G/5G) | < 1.5초 | > 5초 |

## 3. 동시 수정 충돌 (409 CONFLICT)

### 3-1. 충돌 발생 시나리오

두 명이 거의 동시에 같은 필드를 수정하고 거의 동시에 [저장] 누른 경우, 두 번째 [저장] 은 BE 가 409 CONFLICT 로 거부합니다.

```
[김영업]                          [박영업]
14:32:00 메모 "긴급 출고" 입력
14:32:01 메모 "오전 배송" 입력
14:32:02 [저장] → 200 OK ✅
14:32:03                           [저장] → 409 CONFLICT ❌
14:32:04 SSE 토스트 수신:          빨간 토스트:
   "내가 방금 저장 ✅"             "다른 사용자가 먼저 저장했습니다.
                                    화면을 새로고침하여 최신 값을 확인하세요."
```

### 3-2. 충돌 시 화면 표시

박영업 화면에는 다음 3가지가 동시에 나타납니다.

1. **빨간 토스트** — `다른 사용자가 먼저 저장했습니다. 화면을 새로고침하여 최신 값을 확인하세요.`
2. **저장 버튼 disabled** — 새로고침 전까지 추가 저장 불가
3. **메모 필드 audit overlay** — 김영업의 새 값(`긴급 출고`) + 취소선으로 박영업의 입력(`오전 배송`) 표시

### 3-3. 대처 절차

1. 박영업 화면 새로고침(`Ctrl + F5`) — 김영업의 최신 값으로 화면 초기화
2. 박영업이 다시 메모 입력 — 김영업의 값을 보고 있으므로 의도적 변경 (예: `긴급 출고 + 오전 배송 부탁`)
3. [저장] → 200 OK + audit log 에 박영업 새 revision 누적

> **원칙** — Phase 12 실시간 동기화는 "마지막 저장 우선(last-write-wins)" 이 아니라 "동시 충돌 명시 후 재입력(explicit retry)" 입니다. 한국 일반기업회계기준 거래 보존 원칙에 따라 어느 한 쪽이 일방적으로 덮어쓰는 것을 방지합니다.

## 4. 운영 변경 안내 (이전 vs Phase 12)

| 측면 | 이전 (Phase 12 이전) | 변경 (Phase 12) |
| --- | --- | --- |
| 화면 갱신 | 수동 새로고침(`Ctrl + F5`) | SSE 자동 갱신 (1초 이내) |
| 다른 사람 변경 사실 인지 | 새로고침 후 비로소 발견 (또는 영영 모름) | 즉시 토스트 + audit overlay |
| 동시 수정 충돌 | 마지막 저장이 무조건 덮어씀 (silent overwrite) | 409 CONFLICT + 빨간 토스트 + 새로고침 강제 |
| 변경자 식별 | "어제 누가 바꿨는지" 알려면 IT 관리자 audit log 조회 요청 | 화면 안에서 색상 dot + 풀네임 즉시 확인 |
| 적용 범위 | 일부 화면만 | 17 service / 50+ desktop page + mobile-staff 일괄 |

## 5. FAQ

| 증상 | 원인 | 해결 |
| --- | --- | --- |
| 다른 사람이 저장했는데 내 화면이 안 바뀜 | SSE 연결 끊김 | `Ctrl + F5` 새로고침 후 자동 재연결 |
| 토스트가 너무 자주 떠서 작업 방해 | 같은 항목을 다수가 동시 수정 중 | 작업 협의 후 한 명씩 순차 저장 권장 |
| 새로고침 했는데도 옛 값이 보임 | 브라우저 캐시 / 서비스 워커 | `Ctrl + Shift + R` 강제 새로고침 |
| 사내 LAN 인데 동기화가 5초 걸림 | gateway / Redis pub-sub 점검 필요 | IT 관리자에게 `samhan.realtime.*` health check 요청 |
| 모바일에서 동기화 안 됨 | mobile-staff WebSocket 권한 부족 | 앱 재시작 + 로그인 재진행 ([06-트러블슈팅/04. 모바일 접속 오류](../06-트러블슈팅/04-모바일-접속-오류.md)) |
| 토스트가 한국어가 아닌 영어 / 깨진 문자 | 브라우저 인코딩 / 폰트 누락 | Edge / Chrome 권장 + Noto Sans KR 시스템 설치 |
| 408 Request Timeout 표시 | SSE 장시간 idle (8시간+) | 새로고침 → 자동 재연결 (정상) |
