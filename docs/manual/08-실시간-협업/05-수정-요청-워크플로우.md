# 08-실시간-협업 / 05. 수정 요청 워크플로우 (Stage 4)

> ✅ **구현 상태** — Phase 12 step-3 (PR-H3) `SlipEditRequestDialog` + 잠금 정책 + SSE 알림 5채널 완성. PR-H4b/4c 부터 다른 service (거래처/재고/세금계산서/배차/사용자 등) 도 동일 패턴 적용.
>
> **본 docs 는 무엇인가요?** — 잠긴 항목(슬립/거래처/재고/배차 등)을 수정해야 할 때 권한자(MANAGER+/MASTER)에게 사유를 적어 명시적으로 요청하고, 수락 시 임시 unlock 받아 직접 수정한 후 자동 재잠금되는 전체 흐름을 안내합니다.

---

## 대상 독자

- **모든 운영자** — 본인이 작성/처리한 항목이지만 잠금 단계 (1차/2차) 에 진입하여 수정 불가한 경우
- **MANAGER / MASTER** — 수정 요청을 받고 수락/거절 결정
- 사전 준비: [00. 실시간 협업 개요](00-실시간-협업-개요.md), [06. 잠금 정책](06-잠금-정책.md)

---

## 이 매뉴얼에서 배울 내용

1. 수정 요청 다이얼로그 (사유 + 항목 체크) 입력 절차
2. 권한자 측 검토 / 수락 / 거절 화면
3. 수락 후 본인 측 unlock banner + 카운트다운
4. SSE 실시간 알림 5채널 (요청 / 수락 / 거절 / 만료 / 삭제)
5. 1차 / 2차 잠금 차이 (사유 글자 수 / 카테고리 / unlock 시간)

---

## 1. 1차 잠금 — 수정 요청 절차

### 1-1. 적용 대상

`SENT`, `ACCEPTED`, `PROCESSING`, `REJECTED` status 슬립 (또는 동일 잠금 단계의 다른 service 항목).

### 1-2. 흐름도

```
[본인 영업: 김영업]                  [MANAGER: 박관리]
  슬립 상세 → [✏ 수정 요청]
       ↓
  SlipEditRequestDialog
   - 사유 입력 (50자 권장)
   - 수정 항목 체크 (메모/품목/배송지/...)
   - [요청 보내기]                  → SSE 토스트:
                                      "김영업이 슬립 #001 수정 요청"
                                      ↓
                                    [수정 요청 검토] 다이얼로그
                                     - 사유 검토
                                     - 검토 의견 입력 (선택)
                                     - [수락] / [거절]
       ↑                                  ↓
       SSE 토스트: "수정 요청 수락 (24시간 내 수정 가능)"
       ↓
  슬립 상세 → 노란 banner: "수정 가능 23:48 남음"
       ↓
  필드 자유 편집 → [저장] → 자동 재잠금 + audit log 누적
```

### 1-3. 단계별 화면

#### Step 1 — 본인 측 [✏ 수정 요청] 버튼 클릭

슬립 상세 헤더 우측에 **[✏ 수정 요청]** 버튼이 표시됩니다 (1차/2차 잠금 status 에서만 노출).

#### Step 2 — SlipEditRequestDialog 입력

![SlipEditRequestDialog 작동 캡처](https://github.com/ewoo14/SamhanLogis/raw/24b22f9/docs/qa/phase-12-step-3-slip-edit-permission/working-edit-request-dialog.png)

| 입력 | 비고 |
| --- | --- |
| 사유 | 50자 권장 (1차 잠금) — 빈 값 시 [요청 보내기] 회색 |
| 수정 항목 체크 | 메모 / 품목 / 배송지 / 검수지 / 결제정보 등 다중 선택 |
| 비고 (선택) | 추가 설명 |
| [요청 보내기] | 클릭 시 BE `POST /slips/{id}/edit-requests` 호출 |

#### Step 3 — 권한자 측 SSE 알림

권한자 (MANAGER+) 화면 우측 상단 토스트 + 슬립 헤더 `수정 요청 검토 중` badge 즉시 노출.

```
  사유: 거래처에서 품목 수량을 4 → 6 으로 변경 요청. 재고 가능 확인 완료.

```

## 2. 2차 잠금 — 검수/배송 단계 수정 요청 (사유 200자 + 카테고리)

### 2-1. 적용 대상

`INSPECTING`, `COMPLETED`, `SHIPPING`, `DELIVERED` status 슬립.

### 2-2. 1차와 다른 점

| 항목 | 1차 | 2차 |
| --- | --- | --- |
| 사유 글자 수 | 50자 권장 | **200자 이상 강제** |
| 비즈니스 카테고리 | 없음 | **거래처 요청 / 재고 차질 / 법적 사유 / 기타** 4 옵션 중 1개 필수 |
| 수락자 | MANAGER (즉시 수락) | MASTER (MANAGER 는 검토 의견만 첨부 가능) |
| unlock 시간 | 24시간 | **1시간** (긴급 처리 강제) |
| audit log | 누적 | **영구 보존 + 감사 표시** |
| banner 색상 | 노랑 | 빨강 (위험 강조) |

> **운영 의미** — 검수 중에 거래처가 수량 변경을 요청하는 일이 흔하지만 이미 재고 예약(reserve)이 진행되었기에 함부로 변경하면 회계/재고 정합성 위험. 2차 잠금은 이 위험을 명시화하여 MASTER 의 결재가 필수임을 강제합니다.

## 3. 삭제 요청 절차

### 3-1. 흐름도

```
[본인 영업]                          [MANAGER+ / MASTER]
  슬립 상세 → [⌫ 삭제 요청]
       ↓
  SlipDeleteRequestDialog
   - 사유 입력 (필수)
   - "삭제 = soft delete + CANCELED status"
   - [요청 보내기]                  → [수락] → 즉시 삭제
                                      ↓
                                    슬립 status = CANCELED
                                    deleted_at = now()
                                    audit log 영구 보존
       ↑
       SSE 토스트: "슬립이 삭제되었습니다.
                  관련 분개는 회계팀에 통보됨"
```

### 3-2. status 별 삭제 권한

| status | 삭제 가능? | 절차 |
| --- | --- | --- |
| `DRAFT` / `SAVED` | ✅ 본인 즉시 | 요청 절차 없이 [⌫ 삭제] |
| `SENT` ~ `DELIVERED` | ✅ 요청 후 MANAGER+ 수락 시 | SlipDeleteRequestDialog |
| `CONFIRMED` | ❌ 불가 | 회계 역분개 절차로만 처리 |
| `CANCELED` | (이미 취소) | 신규 슬립 발행으로 대체 |

> **삭제 방식** — soft delete (`deleted_at` 컬럼 set + 화면 hide). audit log 는 영구 보존되어 감사 시점 추적 가능.

## 4. SSE 실시간 알림 채널 (PR-H3 5종 신규)

PR-H1 의 `SlipRealtimeClient` 위에서 5종 신규 채널 추가:

| 이벤트 | 발행 시점 | 수신자 | 토스트 메시지 |
| --- | --- | --- | --- |
| `edit.requested` | 수정 요청 보낼 때 | 수락자 (MANAGER+/MASTER) | `김영업이 슬립 #N 수정 요청 (사유: ...)` |
| `edit.accepted` | 수락자가 수락할 때 | 요청자 | `수정 요청이 수락되었습니다 (24시간 내 수정 가능)` |
| `edit.rejected` | 수락자가 거절할 때 | 요청자 | `수정 요청이 거절되었습니다. 사유: ...` (빨강) |
| `edit.unlock_expired` | 24h/1h 타이머 만료 | 요청자 | `수정 가능 시간이 만료되었습니다. 슬립이 다시 잠겼습니다.` |
| `delete.accepted` | 삭제 요청 수락 시 | 요청자 + 회계담당 | `슬립이 삭제되었습니다. 관련 분개는 회계팀에 통보됨` |

## 5. unlock banner — 카운트다운 색상

수락 후 본인 측 화면 상단에 카운트다운 banner 가 노출됩니다.

| 남은 시간 (1차 24h 기준) | banner 색상 | 의미 |
| --- | --- | --- |
| 23:48 ~ 12:00 | 노랑 | 정상 범위 |
| 12:00 ~ 1:00 | 주황 | 마무리 권장 |
| 1:00 ~ 0:00 | 빨강 + 깜빡 | 임박 |
| 0:00 도달 | 회색 banner "잠금 복귀" | 자동 잠금 — 다시 요청 필요 |

> 2차 잠금 1h 의 경우 동일 비율로 압축 (예: 30분~10분 = 노랑, 10분~5분 = 주황, 5분~0분 = 빨강).

## 6. 거절 처리

### 6-1. 거절 사유 입력

권한자가 [거절] 클릭 시 거절 사유 입력 다이얼로그가 추가로 노출됩니다.

```
+────────────────────────────────────────────────+
│  수정 요청 거절 — 사유 입력                      │
+────────────────────────────────────────────────+
│  거절 사유                                       │
│  ┌──────────────────────────────────────────┐ │
│  │ 검수 단계 진행 완료 — 수량 변경 시 재고  │ │
│  │ 정합성 위험. 거래처에 분할 발행 요청     │ │
│  │ 권장.                                       │ │
│  └──────────────────────────────────────────┘ │
+────────────────────────────────────────────────+
│  [ 취소 ]                  [ 거절 확정 ]         │
+────────────────────────────────────────────────+
```

거절 사유는 PR-H2 audit log `editRequestRejection` 컬럼에 영구 기록됩니다.

### 6-2. 요청자 측 거절 토스트

```
[ ✗ 수정 요청이 거절되었습니다 ]
  수락자: 박관리 (영업관리팀장 / MANAGER)
  사유: 검수 단계 진행 완료 — 수량 변경 시 재고 정합성 위험.
        거래처에 분할 발행 요청 권장.
  [ 다시 요청 ]   [ 닫기 ]
```

### 6-3. 재요청 가능

거절된 요청은 새 사유로 재요청 가능. 단, audit log 에 거절 이력 영구 기록.

## 7. 운영 변경 안내 (이전 vs PR-H3)

| 측면 | 이전 (PR-H3 이전) | 변경 (PR-H3) |
| --- | --- | --- |
| 잠금 정책 | DRAFT/SAVED 외에는 영업 직접 수정 불가 (관리자 직접 수정만) | 4단계 잠금 (0/1/2/영구) — 본인이 요청 → 수락 시 임시 unlock |
| 2차 잠금 사유 | 사유 입력 없음 | 200자 + 비즈니스 카테고리 + audit log 영구 |
| 알림 | 화면 새로고침 후 확인 | SSE 실시간 토스트 + 헤더 badge |
| 수정 시간 제한 | 없음 (관리자가 언제든 수정) | 1차 24h / 2차 1h — 시간 만료 시 자동 잠금 |
| 거절 사유 | 구두 전달 | audit log `editRequestRejection` 컬럼 영구 보존 |
| 삭제 | hard delete (DB row 제거) | soft delete + CANCELED status + audit log 보존 |

## 8. FAQ

| 증상 | 원인 | 해결 |
| --- | --- | --- |
| `[✏ 수정 요청]` 버튼이 안 보임 | DRAFT/SAVED status (잠금 없음) — 직접 수정 가능 | 슬립 본문 필드 직접 편집 |
| `[✏ 수정 요청]` 버튼이 회색 | CONFIRMED 또는 CANCELED status | CONFIRMED → 회계 역분개 / CANCELED → 신규 발행 |
| 사유 입력했는데 [요청 보내기] 가 회색 | 2차 잠금인데 200자 미달 또는 카테고리 미선택 | 사유 200자 + 카테고리 1개 선택 |
| 수정 요청 후 알림이 안 옴 | SSE 연결 끊김 | 페이지 새로고침 → 자동 재연결 |
| 수락 후 banner 시간이 정확하지 않음 | 클라이언트 시계 차이 | BE 가 server time 기준 — 새로고침 후 재계산 |
| 시간 만료 직전에 저장하면? | 저장 시점에 BE 가 unlock 만료 검증 → 만료 시 409 CONFLICT | 만료 직전이면 다시 요청 필요 (재요청은 새 audit log 항목) |
| 거절된 요청을 다시 보낼 수 있나요? | 가능 — 새 사유로 재요청 | audit log 에 거절 이력 영구 기록 |
| 본인 외에 누가 수정 요청 가능한가요? | SALES 다른 직원은 불가, MANAGER+ 는 직접 수정 가능 | MANAGER 에게 직접 수정 요청 |
| 모바일에서도 수정 요청 가능한가요? | mobile-staff 동일 패턴 적용 | [08. 모바일 실시간 알림](08-모바일-실시간-알림.md) 참조 |
| 동시에 여러 요청을 보내도 되나요? | 같은 슬립에 동시 1건만 (이전 요청 종료 전 신규 요청 차단) | 이전 요청 [요청 취소] 후 재요청 |
