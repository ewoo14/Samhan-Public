# 04-모바일 / 04. 현장 사진 첨부 (Stage 3 — 미구현 안내)

> 구현 상태 — 미구현 P1 신규 catalog sub 추가 권고 — 현장 사진 + slip attachment. 본 매뉴얼은 향후 구현 예정 안내 + 임시 대응 (이메일/카톡 별도 전송) 만 제공

## 대상 독자

- 배송 기사(DRIVER) — 현장 도착 시 차량 / 화물 / 인수 사진 촬영 필요
- 영업팀(SALES) — 분쟁 시 현장 증빙 사진 요청
- 영업 관리자(MANAGER) / MASTER — 사진 첨부 정책 결정
- 회계팀(ACCOUNTANT) — 매출 증빙 시 부수 자료

## 1. 미구현 현황

### 1-1. 본 기능 = 완전 미구현

> 현재 mobile-staff (driver mode / estimate mode) 양쪽 모두 **사진 촬영 / 첨부 / slip 연동 기능이 없습니다.**

| 영역 | 구현 여부 |
| --- | --- |
| **mobile-staff 카메라 권한 요청** | 없음 |
| **사진 촬영 화면 (RN)** | 없음 |
| **사진 업로드 endpoint** | 없음 |
| **slip-service attachment 컬럼** | 없음 (V12 schema 신규 필요) |

| **admin web 사진 미리보기 UI** | 없음 |

## 2. 향후 구현 시나리오 (참고)

### 2-1. 시나리오 1 — 배송 현장 사진 (driver mode)

배송 기사가 정차 도착 시 화물 상태 / 인수 현장 사진 촬영.

```
┌─ 정차 도착 ─────────────────────────┐
│                                       │
│  1. [정차 도착] 버튼 탭               │
│  2. [사진 첨부] 버튼 자동 노출        │
│  3. 카메라 진입 → 사진 1~5장 촬영     │
│  4. 자동 압축 (1080×1920 JPEG ≤500KB)│
│  5. backend 업로드 (file-server)     │
│  6. 업로드 완료 후 [서명 받기] 진입   │
│                                       │
└───────────────────────────────────────┘
```

### 2-2. 시나리오 2 — 견적 현장 사진 (estimate mode)

영업 직원이 견적 현장 답사 시 설치 위치 사진 촬영.

```
┌─ 견적 작성 ─────────────────────────┐
│                                       │
│  1. [전표작성] 거래처 form           │
│  2. [현장 사진] 버튼 탭               │
│  3. 카메라 진입 → 1~10장 촬영         │
│  4. 견적 라인에 자동 첨부 (메타)      │
│  5. 견적서 인쇄 시 사진 부록 페이지   │
│                                       │
└───────────────────────────────────────┘
```

### 2-3. 시나리오 3 — 분쟁 시 사후 첨부 (admin)

분쟁 발생 시 영업/회계가 PC 에서 슬립 상세 → [+ 사진 첨부] → 파일 업로드.

## 3. 임시 대응 — 별도 전송

본 기능 정식 구현 전까지 다음 임시 우회를 사용합니다.

### 3-1. 카카오톡 별도 전송 (권장)

기사 / 영업 직원이 핸드폰 카메라로 직접 촬영 → 카카오톡 사내 그룹채팅에 업로드 → 영업 / 회계가 PC 에서 다운로드.

| 단계 | 동작 |
| --- | --- |
| **1. 촬영** | 핸드폰 기본 카메라 |
| **2. 전송** | 사내 카카오톡 그룹 (예: `삼한물류 - 배송증빙`) |
| **3. 분류** | 메시지 본문에 `슬립번호 + 정차명 + 일자` 명시 (예: `S-2026-00321 / 강남2호점 / 2026-05-09`) |
| **4. 보존** | 회계 직원이 매월 말 사진 폴더 정리 후 백업 |

> 카카오톡 보관 기간 = 5GB 무료 + 사진 30일 자동 만료. 30일 내 회계 정리 필수.

### 3-2. 이메일 (장기 보존 필요 시)

분쟁 / 감사 / 법적 증빙 필요 시 이메일 권장 (장기 보존 + 검색 용이).

| 항목 | 권장 |
| --- | --- |
| **수신** | 영업 관리자 + 회계팀 (사내 ML) |
| **제목** | `[배송증빙] {슬립번호} {거래처명} {일자}` |
| **본문** | 정차 / 인수자 / 비고 |
| **첨부** | JPEG 사진 (압축 후) |

### 3-3. 사진 폴더 공유 (대량)

대량 사진 (월말 일괄) → Google Drive / OneDrive 사내 폴더 업로드.

| 폴더 구조 권장 |
| --- |
| `삼한물류/배송증빙/2026-05/S-2026-00321 - 강남2호점/` |
| 폴더 안 사진 5~10장 + `메모.txt` (특이사항) |

### 3-4. 사용자 분쟁 시 흐름

1. 거래처 분쟁 접수 (인수 거부 / 화물 파손 등)
2. 영업이 기사 카카오톡 / 이메일에서 해당 슬립 사진 검색
3. 사진 다운로드 → 거래처 회신 + 회계 이의제기 첨부
4. 분쟁 해결 후 슬립 status / 매출 조정

## 4. 정식 구현 시 변경될 흐름

본 기능 정식 활성 시 다음과 같이 통합됩니다.

### 4-1. driver mode — 정차 도착 → 사진 → 서명 1 흐름

| 현재 | 정식 활성 후 |
| --- | --- |
| 정차 도착 → [서명 받기] 즉시 | 정차 도착 → [사진 첨부 (선택)] → [서명 받기] |
| 사진은 카카오톡 별도 | 사진은 slip 에 자동 첨부 (file-server) |
| 분쟁 시 카카오톡 검색 | admin web 슬립 상세에서 즉시 미리보기 |

### 4-2. slip-service schema 변경 (V12 예상)

```sql
-- 신규 table (예시 — 정식 설계 시 변경 가능)
CREATE TABLE slip_attachments (
  id UUID PRIMARY KEY,
  slip_id UUID NOT NULL REFERENCES slips(id),
  stop_seq INT,                  -- driver mode 시 정차 번호
  attachment_type VARCHAR(20),   -- PHOTO_DELIVERY / PHOTO_SITE / DOC_INVOICE 등
  file_url TEXT NOT NULL,        -- file-server / S3 URL
  file_size_bytes INT NOT NULL,  -- 5MB 가드
  mime_type VARCHAR(50) NOT NULL,
  uploaded_by UUID,              -- actor
  uploaded_at TIMESTAMPTZ NOT NULL,
  ...BaseEntity 7 audit
);
```

### 4-3. 파일 가드 (정식 활성 시 예정)

| 가드 | 값 | 비고 |
| --- | --- | --- |
| **단일 파일 크기** | ≤5 MB | JPEG 자동 압축 |
| **슬립당 첨부 수** | ≤20장 | 대량 방지 |
| **MIME type** | image/jpeg / image/png / application/pdf | exe / sh 차단 |
| **저장소** | file-server (Phase 11 production 시 S3) | 공개 URL 미발급 (signed URL only) |
| **보존 기간** | 5년 (분쟁 시효 고려) | 회계 정책 별도 결정 |

### 4-4. UI 노출 가드

| 가드 | 동작 |
| --- | --- |
| **UUID 비공개** | `slipNo` + `정차명` + `일자` 만 노출. attachment UUID 미노출 |
| **권한 분리** | DRIVER = 본인 업로드만 / SALES = 본인 슬립만 / MANAGER = 전체 / ACCOUNTANT = 전체 (read) |
| **삭제 가드** | 업로드 후 24시간 내 본인만 삭제 가능 / 이후 MANAGER 만 |

## 5. 자주 묻는 질문 + 트러블슈팅

| 증상 | 원인 | 해결 |
| --- | --- | --- |
| mobile-staff 에 [사진 첨부] 버튼이 없음 | 정식 미구현 | 본 매뉴얼 §3 임시 우회 사용 |
| 카카오톡 사진이 30일 후 사라짐 | 카카오톡 보관 정책 | 회계 직원이 매월 말 정리 + 사내 Drive 업로드 |
| 거래처가 사진 증빙 요구 | 분쟁 시 즉시 회신 필요 | 본 §3-4 흐름 사용 |
| 기사가 사진 누락 | 카카오톡 업로드 안 함 | 영업 / 배차 담당이 매일 / 매주 점검 |
| 정식 기능 언제 활성? | Phase 11 production 후 별도 PR | 일정 미확정 — 사용자 결정 대기 |
| 임시 우회로 충분한가? | 소량 운영은 충분, 대량 / 분쟁 다수 시 부족 | 정식 활성 우선순위 P1 검토 |
| 사진 백업이 사라짐 | 카카오톡 만료 + Drive 미업로드 | 매월 말 일괄 정리 SOP 권장 |

## 6. 사용자 결정 권고 (개발팀 → 사용자)

본 기능은 P1 (P0 보다 낮음) 으로 분류되며, 다음 시나리오 중 사용자 결정 필요.

### 옵션 A — Phase 11 production 후 즉시 P1 활성

- 장점: 분쟁 시 즉시 증빙 + 영업 효율
- 단점: Phase 11 후 추가 4~6주 개발 필요

### 옵션 B — Phase 12 후 검토 (장기 보류)

- 장점: Phase 11 안정화 우선 + 임시 우회 (카카오톡) 로 운영 지속
- 단점: 대량 / 분쟁 증가 시 운영 부담

### 옵션 C — 하이브리드 (driver mode 만 우선)

- driver mode 의 배송 사진만 우선 활성 (P1) → estimate mode 견적 사진은 Phase 12 (P2)
- 장점: 가장 시급한 분쟁 증빙 우선 해결
- 단점: 양쪽 별도 개발

> 본 결정은 사용자 + 회계 / 영업 책임자가 합의 후 PM 에게 전달. 결정 시 누락 catalog 의 P1 sub 가 확정 추가됨.
