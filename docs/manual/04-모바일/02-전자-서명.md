# 04-모바일 / 02. 전자 서명 받기 (Stage 3)

> 구현 상태 — 완료 slip-service `/public/batches/.../signature` (LINK source) + arologis-service `/driver-app/.../sign` (APP source) + V10 `signature_source` 컬럼 + V11 동시성 인덱스 + 50KB PNG hash 가드 + DELIVERED 자동 전이
>
> 미구현 부분: P0-9 (관리자 web 화면 슬립 상세에서 서명 이미지 미리보기 — 현재 GET API 만 가능), 서명 무효화 audit UI

---

## 대상 독자

- 배송 기사(DRIVER) — 정차별 인수자 서명 캡처
- 영업팀(SALES) — 모바일 서명 batch 발송 + 진행 확인
- 영업 관리자(MANAGER) / MASTER — 서명 audit 검토
- 사전 준비: [01. 기사 앱](01-기사-앱.md) 의 driver mode 로그인 완료, 서명 대상 슬립이 INSPECTING / COMPLETED / SHIPPING status

---

## 이 매뉴얼에서 배울 내용

1. 전자 서명 2가지 발급 경로 (LINK / APP)
2. 모바일 어플 서명 (APP) 전체 흐름 — 캡처 → hash 검증 → 50KB 가드 → 저장
3. SMS/Aligo 링크 서명 (LINK) 흐름 — 영업 batch 발송 + 인수자 외부 진입
4. 서명 후 슬립 status 자동 전이 (`DELIVERED`)
5. 서명 audit 추적 (RECORD / INVALIDATE)

---

## 1. 전자 서명 2가지 경로

slip-service 의 `signature_source` 컬럼은 서명 발급 경로를 식별합니다.

| source | 발급 경로 | 입력 매체 | 사용 시점 |
| --- | --- | --- | --- |
| **LINK** | SMS/Aligo 링크 → 인수자 외부 모바일 진입 | 인수자 본인 핸드폰 | 거래처 인수자가 현장 서명 불가 / 후일 정리 |
| **APP** | 기사 앱 (`mobile-staff` driver mode) | 배송 기사 핸드폰 | 정차 도착 시 기사가 인수자에게 직접 받음 |

> 두 경로 모두 **인수자 본인** 의 서명입니다. APP source 도 기사가 대신 서명하지 않으며, 핸드폰을 인수자에게 건네 직접 받습니다 (감사 회피).

## 2. 모바일 어플 서명 (APP source)

### 2-1. 사전 조건

- 배송 기사가 정차에 도착
- 슬립 status = `INSPECTING` / `COMPLETED` / `SHIPPING` 중 하나
- 인수자가 현장에 있음

### 2-2. Step 1 — 정차 선택

기사 앱 dashboard → 차량 카드 탭 → [정차 목록] → 도착한 정차 → [서명 받기].

![정차 목록에서 서명 받기 진입](../screenshots/04-모바일/02-signature-stop-select.png)

### 2-3. Step 2 — 서명 캔버스

`DriverSignatureScreen` 의 캔버스가 표시됩니다.

![서명 캔버스 화면](../screenshots/04-모바일/02-signature-canvas.png)

| 요소 | 설명 |
| --- | --- |
| **인수자명 input** | 서명 전 인수자 이름 입력 (1~50자) |
| **캔버스 영역** | 손가락 / stylus 로 직접 서명 |
| **[지우기]** | 다시 받기 |
| **[캡처]** | PNG + GPS 동시 캡처 |
| **[전송]** | backend 전송 |

### 2-4. Step 3 — 캡처 (PNG + GPS 동시)

[캡처] 버튼 탭 시점에 다음이 1회 캡처됩니다.

| 캡처 항목 | 형식 | 비고 |
| --- | --- | --- |
| **서명 PNG** | base64 dataURL | 캔버스 자동 압축 → ≤50KB 보장 |
| **GPS latitude** | NUMERIC(10,7) | ~1.1cm 정확도 |
| **GPS longitude** | NUMERIC(10,7) | ~1.1cm 정확도 |
| **capturedAt** | ISO-8601 | 클라이언트 시각 (서버가 재기록) |

### 2-5. Step 4 — 전송

[전송] 탭 → backend POST → 응답 alert.

```http
POST /driver-app/arologis/dispatches/{id}/vehicles/{seq}/stops/{stopSeq}/sign
Authorization: Bearer <DRIVER JWT>
Content-Type: application/json

{
  "imageRef": "data:image/png;base64,iVBORw0KGgoAAA...",
  "latitude": 37.5665,
  "longitude": 126.9780
}
```

응답:

```json
{
  "signatureId": "(자동 발급)",
  "slipBridged": true
}
```

| 필드 | 의미 |
| --- | --- |
| `signatureId` | 서명 record ID (UUID — 사용자 미노출, 감사용) |
| `slipBridged` | `true` = arologis + slip-service 양쪽 저장 / `false` = arologis 만 |

### 2-6. Step 5 — slip-service 자동 전파

arologis-service 가 다음 internal endpoint 로 slip-service 에 자동 전파.

```http
POST /internal/slips/{slipId}/signatures
X-Service-Source: arologis-service

{
  "signerName": "...",
  "imagePngBase64": "...",
  "imageHashSha256": "...",
  "channel": "MOBILE_CANVAS",
  "source": "APP",
  "capturedAt": "2026-05-09T10:30:00+09:00",
  "latitude": 37.5665,
  "longitude": 126.9780
}
```

### 2-7. Step 6 — slip-service 저장 + status 전이

slip-service 가 다음 검증 + 저장 처리.

1. **PNG 크기 가드** : ≤50KB (50 × 1024 bytes) — 초과 시 `400 INVALID_INPUT`
2. **PNG SHA-256 재계산** : 클라이언트 hash 와 서버 재계산 hash 비교 → mismatch 시 `400`
3. **signerName 검증** : 1~50자 (DTO @Size + 도메인 가드 2단)
4. **slip status 가드** : `INSPECTING` / `COMPLETED` / `SHIPPING` 만 허용 → 다른 status 시 `409 CONFLICT`
5. `slips.signature_source = 'APP'` 기록
6. `slip_signature_audit` INSERT (RECORD action)
7. **`slips.status` → `DELIVERED` 자동 전이**
8. `signed_at` / `signer_name` / `signature_image_hash` 컬럼 업데이트

> APP source 의 slip status 자동 전이는 LINK source 와 동일한 트랜잭션 흐름. 양쪽 모두 `DELIVERED` 로 한 번에 진입.

### 2-8. Step 7 — 영업 / 회계 즉시 확인

영업 슬립 목록 / 회계 분개 입력 화면에서 status `DELIVERED` 즉시 노출. 새로고침 불필요 (실시간 polling 5초).

## 3. SMS/Aligo 링크 서명 (LINK source)

### 3-1. 영업 batch 발송 (영업 시점)

[01-영업/03. 슬립 발행](../01-영업/03-슬립-발행.md) §7 의 모바일 서명 batch 발송 흐름 참조. 영업이 슬립 INSPECTING 진입 후 [모바일 서명 batch 발송] 클릭 → SMS/Aligo 발송.

### 3-2. 인수자 외부 진입

인수자 핸드폰에 다음 SMS 도착.

```
[(주)삼한공조시스템] 배송 인수 확인 부탁드립니다.
슬립번호: S-2026-00321
링크: https://sign.samhan-air.com/<shareToken>
유효: 24시간
```

링크 진입 → 공개 모바일 서명 화면 (slip-service `/public/signatures/{shareToken}`) → 인수자 본인 핸드폰에서 직접 서명.

### 3-3. 공개 endpoint

실 코드 — `services/slip-service/src/main/java/com/samhanair/logis/slip/delivery/web/PublicSlipController.java#recordSignature` + `PublicSignatureRequest`.

```http
POST /public/batches/{token}/slips/{slipNo}/signature
(인증 X — batch token + slipNo path 로 식별, 서버가 SecurityConfig permitAll 처리)

{
  "signerName": "홍길동",
  "signaturePngBase64": "data:image/png;base64,iVBORw0KGgoAAA...",
  "clientHash": "<SHA-256 hex 64자 — Web Crypto API 클라이언트 계산값>"
}
```

| 필드 | 검증 (DTO `@NotBlank` + `@Size`) |
| --- | --- |
| `signerName` | 1~50자 (인수자 본인 이름) |
| `signaturePngBase64` | PNG data URI 또는 raw base64 (서버 50KB 가드) |
| `clientHash` | SHA-256 hex 정확히 64자 (서버 재계산 후 mismatch 시 400) |

저장 결과: `signature_source = 'LINK'` 기록 + 동일 status 전이 (`DELIVERED`) + share token 발급 응답.

### 3-4. 토큰 만료

shareToken 24시간 만료. 만료 후 진입 시 `410 GONE` 응답 + 안내 화면 ("링크 만료 — 영업에 재발송 요청").

## 4. 서명 audit 추적

### 4-1. audit table (`slip_signature_audit`)

모든 서명 발급 / 무효화 기록.

| 컬럼 | 설명 |
| --- | --- |
| `slip_id` | 대상 슬립 |
| `action` | `RECORD` (발급) / `INVALIDATE` (무효화) |
| `signature_source` | `LINK` / `APP` |
| `actor_user_id` | 무효화 actor (RECORD LINK 는 NULL) |
| `created_at` | 발생 시각 |
| `image_hash_sha256` | PNG hash (검증용) |

### 4-2. 관리자 GET 조회

```http
GET /api/slips/{slipId}/signature
Authorization: Bearer <MASTER/MANAGER JWT>
```

응답: 현재 서명 정보 + audit 이력.

### 4-3. 관리자 무효화

서명 잘못 받음 / 부정 의심 시 무효화.

```http
DELETE /api/slips/{slipId}/signature
Authorization: Bearer <MASTER/MANAGER JWT>
X-User-Id: <actor>
```

처리:
1. `slips.signature_image_hash` / `signed_at` / `signer_name` NULL 처리
2. `slip_signature_audit` INSERT (INVALIDATE action, actor_user_id 보존)
3. slip status 는 변경 X (수동 복귀 필요)

### 4-4. UI 미구현 (P0-9)

현재 admin web 의 슬립 상세 화면에서 서명 이미지 미리보기 / audit 이력 UI 가 미구현입니다 (P0-9). API 호출 후 base64 직접 확인 또는 Phase 11 후 정식 화면 예정.

## 5. 보안 / 감사 가드

| 가드 | 동작 |
| --- | --- |
| **PNG hash 검증** | 클라이언트 hash 와 서버 재계산 hash mismatch → `400 INVALID_INPUT` (위변조 차단) |
| **PNG 크기 가드** | 50KB 초과 → `400` (DoS / 저장 폭증 차단) |
| **status 가드** | INSPECTING/COMPLETED/SHIPPING 만 → 다른 status `409` (DRAFT 슬립에 서명 불가) |
| **shareToken 만료** | 24시간 후 `410 GONE` (장기 노출 차단) |
| **RECORD audit** | LINK source 도 actor=NULL 로 기록 (공개 endpoint, 감사용) |
| **INVALIDATE audit** | actor_user_id 필수 (X-User-Id 헤더) — 누구 무효화했는지 추적 |
| **동시성 인덱스 (V11)** | 동일 slip 두 번 서명 → unique 제약 위반 차단 |

## 6. 자주 묻는 질문 + 트러블슈팅

| 증상 | 원인 | 해결 |
| --- | --- | --- |
| 캔버스가 작동 안 함 | `react-native-signature-canvas` 미설치 (graceful fallback 활성) | IT 관리자에게 정식 build 요청 |
| 전송 실패 — `400 INVALID_INPUT` "PNG too large" | 50KB 초과 | 캔버스 다시 그리기 (자동 압축) |
| 전송 실패 — `400` "hash mismatch" | 이미지 변조 / 네트워크 결함 | 다시 캡처 + 전송 |
| 전송 실패 — `409 CONFLICT` | slip status 가 INSPECTING/COMPLETED/SHIPPING 아님 | 영업에 슬립 status 확인 요청 |
| 전송 성공인데 `slipBridged: false` | slip-service 일시 장애 | 자체 저장은 완료. 자동 재동기화 (Phase 11) — 현재는 IT 관리자 수동 재전파 |
| SMS 링크 진입 시 `410 GONE` | shareToken 24시간 만료 | 영업에 재발송 요청 |
| 서명 후 status `DELIVERED` 전이 안 됨 | slip-service Eureka 미등록 / batch transactional rollback | IT 관리자 문의 |
| 무효화 후 다시 발급하고 싶음 | INVALIDATE 후 status 는 그대로 | 영업 / MANAGER 가 수동 status 복구 + 재서명 batch |
| 서명 이미지 보고 싶음 | admin web UI 미구현 (P0-9) | API GET `/api/slips/{id}/signature` 직접 호출 |
| GPS 캡처 실패 | 실내 약전계 / 권한 일시 회수 | [01. 기사 앱](01-기사-앱.md) §7 GPS 차단 안내 |
| 인수자 이름 못 받음 | 영업이 거래처 마스터 미등록 | [01-영업/01. 거래처 등록](../01-영업/01-거래처-등록.md) 의 인수자 정보 입력 후 재시도 |
