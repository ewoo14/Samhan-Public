## 대상 독자

- 영업팀(SALES) — 발송 / 취소 권한
- 창고팀(WAREHOUSE / INVENTORY) — 접수 / 처리 / 검수 / 출하 / 배송 권한
- 회계팀(ACCOUNTANT) — 정산(CONFIRMED) 권한
- 부서장(MANAGER) — 거절(REJECTED) 권한 + 전 단계 가능
- MASTER — 전 단계 + 서명 삭제 등 시스템 전체

## 1. 결재 단계 (11 status)

```
DRAFT ─save→ SAVED ─send→ SENT ─accept→ ACCEPTED ─process→ PROCESSING
       │                        │
       │                        ↓ inspect
       │                  INSPECTING ─complete→ COMPLETED ─ship→ SHIPPING
       │                                                              │
       │                                                              ↓ deliver
       │                                                          DELIVERED
       │                                                              │
       │                                                              ↓ confirm
       │                                                         CONFIRMED ★
       │                                                       (자동 분개 생성)
       │
       ↓ cancel (DRAFT/SAVED/SENT 만)
   CANCELLED
       │
       ↓ reject (MANAGER 만, 임의 단계)
    REJECTED
```

### 1-1. 단계별 의미

| 단계 | 의미 | 다음 가능 단계 |
| --- | --- | --- |
| **DRAFT** | 신규 등록, 저장 안 함 | SAVED, CANCELLED |
| **SAVED** | 저장 완료 (수정 가능) | SENT, CANCELLED |
| **SENT** | 창고로 발송 (재고 예약) | ACCEPTED, CANCELLED, REJECTED |
| **ACCEPTED** | 창고 접수 | PROCESSING, REJECTED |
| **PROCESSING** | 출고 작업중 | INSPECTING, REJECTED |
| **INSPECTING** | 검수중 | COMPLETED, REJECTED |
| **COMPLETED** | 검수 완료 | SHIPPING, REJECTED |
| **SHIPPING** | 출하 (트럭 적재) | DELIVERED, REJECTED |
| **DELIVERED** | 배송 완료 (서명 수신) | CONFIRMED, REJECTED |
| **CONFIRMED** | 회계 정산 + 자동 분개 | (terminal) |
| **REJECTED** | 거절됨 | (terminal — 영업이 재발행 가능) |
| **CANCELLED** | 취소됨 | (terminal) |

## 2. 권한 매트릭스

각 단계 전이는 **전이 전 status × ROLE × endpoint** 의 조합으로 enforce 됩니다 (slip-service `SlipController` ROLE annotation 기준).

### 2-1. 단계 전이 권한 표

| 전이 (endpoint) | SALES | WAREHOUSE | INVENTORY | ACCOUNTANT | MANAGER | MASTER |
| --- | :-: | :-: | :-: | :-: | :-: | :-: |
| 신규 (`POST /slips`) | ✅ | ❌ | ❌ | ❌ | ✅ | ✅ |
| 헤더 수정 (`PATCH /slips/{id}/header`) | ✅ | ❌ | ❌ | ❌ | ✅ | ✅ |
| 라인 추가/삭제 | ✅ | ❌ | ❌ | ❌ | ✅ | ✅ |
| `save` (DRAFT→SAVED) | ✅ | ❌ | ❌ | ❌ | ✅ | ✅ |
| `send` (SAVED→SENT) | ✅ | ❌ | ❌ | ❌ | ✅ | ✅ |
| `accept` (SENT→ACCEPTED) | ❌ | ✅ | ✅ | ❌ | ✅ | ✅ |
| `process` (ACCEPTED→PROCESSING) | ❌ | ✅ | ✅ | ❌ | ✅ | ✅ |
| `inspect` (PROCESSING→INSPECTING) | ❌ | ✅ | ✅ | ❌ | ✅ | ✅ |
| `complete` (INSPECTING→COMPLETED) | ❌ | ✅ | ✅ | ❌ | ✅ | ✅ |
| `ship` (COMPLETED→SHIPPING) | ❌ | ✅ | ✅ | ❌ | ✅ | ✅ |
| `deliver` (SHIPPING→DELIVERED) | ❌ | ✅ | ✅ | ❌ | ✅ | ✅ |
| **`confirm` (DELIVERED→CONFIRMED) + 자동 분개** | ❌ | ❌ | ❌ | ✅ | ✅ | ✅ |
| `reject` (임의→REJECTED) | ❌ | ❌ | ❌ | ❌ | ✅ | ✅ |
| `cancel` (DRAFT/SAVED/SENT→CANCELLED) | ✅ | ❌ | ❌ | ❌ | ✅ | ✅ |
| 서명 삭제 (`DELETE /slips/{id}/signature`) | ❌ | ❌ | ❌ | ❌ | ❌ | ✅ |

> ⚠️ **button-level RBAC** — 각 ROLE 의 사용자가 슬립 상세 화면에 접근하면 위 표의 ✅ 단계 버튼만 표시됩니다. ❌ 단계는 버튼 자체가 숨겨집니다 (또는 disabled).

### 2-2. ROLE 풀네임 (메모리 가드 `feedback_role_naming_full.md`)

| 풀네임 | 의미 |
| --- | --- |
| **MASTER** | 회사 대표(김미선) + 시스템 슈퍼 관리자 |
| **MANAGER** | 부서장 / 영업총괄 / 창고소장 |
| **SALES** | 영업직원 |
| **WAREHOUSE** | 창고 작업자 (출고 패킹) |
| **INVENTORY** | 재고 관리자 (이동/조정) |
| **ACCOUNTANT** | 회계 담당 |
| **DRIVER** | 배송 기사 (모바일 서명 한정) |

> 본 매뉴얼에서는 약어 (M/M/D 등) 사용 금지 — 항상 풀네임으로 표기.

## 3. 거절 (REJECTED) 처리

### 3-1. 거절 가능 시점

MANAGER (또는 MASTER) 는 **DRAFT 와 CONFIRMED 를 제외한 모든 단계**에서 거절 가능합니다.

- SAVED / SENT — 영업 단계 거절 (잘못된 거래처 / 단가 등)
- ACCEPTED / PROCESSING / INSPECTING — 창고 단계 거절 (재고 부족 발견 / 검수 실패)
- COMPLETED / SHIPPING / DELIVERED — 출하 단계 거절 (배송 사고 / 거래처 수령 거부)

### 3-2. 거절 절차

1. 슬립 상세 → **[거절]** 버튼 (MANAGER 만 표시)
2. 사유 입력 다이얼로그 표시 — 최소 10자 이상 필수
3. **[확인]** → `POST /slips/{id}/reject` body `{ "reason": "..." }`
4. 슬립 status = REJECTED 로 전이 (terminal)
5. 영업 직원에게 알림 발송 (P1-1 — UI 미구현, 현재는 SMS/메일 fallback)

![슬립 거절 다이얼로그](../screenshots/01-영업/04-slip-reject-dialog.png)

### 3-3. 거절된 슬립 재발행

영업 직원 → 거절된 슬립 상세 → **[재발행]** 버튼 → 슬립 복제 (모든 라인 + 헤더 복사) → 신규 DRAFT 슬립 생성 → 사유 수정 후 [저장] [발송].

> 재발행된 슬립은 새 슬립번호 (`S-2026-NNNNN+1`) 가 부여되며, 원본 슬립과 `parentSlipNo` 로 연결됩니다 (V12 migration).

## 4. 취소 (CANCELLED) 처리

### 4-1. 취소 가능 단계

| 단계 | 취소 가능? | 비고 |
| --- | :-: | --- |
| DRAFT | ✅ | 영업 본인만 |
| SAVED | ✅ | 영업 본인 / MANAGER |
| SENT | ✅ | 영업 본인 / MANAGER (재고 예약 자동 해제) |
| ACCEPTED 이후 | ❌ | MANAGER 거절(REJECTED) 만 가능 |

### 4-2. 취소 절차

1. 슬립 상세 → **[취소]** 버튼
2. 확인 다이얼로그 → **[예]**
3. `POST /slips/{id}/cancel` 호출
4. SENT 단계 취소 시 `inventory-service` `POST /inventory/release` 자동 호출 → 재고 예약 해제

## 5. 단계별 알림 / 자동 분개

### 5-1. 알림 (P1-1 — UI 미구현)

| 단계 전이 | 알림 수신자 | 채널 |
| --- | --- | --- |
| SAVED → SENT | 출하창고 담당 (WAREHOUSE) | 헤더 🔔 (P1-1 예정) + SMS fallback |
| SENT → ACCEPTED | 발송한 영업 직원 | 헤더 🔔 |
| INSPECTING → COMPLETED | 영업 + 회계 | 🔔 |
| DELIVERED → CONFIRMED | 영업 + 회계 + MASTER | 🔔 + 자동 분개 알림 |
| 임의 → REJECTED | 발송한 영업 직원 | 🔔 + SMS |

### 5-2. CONFIRMED 시 자동 분개

ACCOUNTANT 가 [정산] 버튼 클릭 → `POST /slips/{id}/confirm` → accounting-service 의 `JournalAutoGenerator` 가 **SLIP_ISSUE 분개** 자동 생성.

| 분개 라인 | 차변 (Dr.) | 대변 (Cr.) | 계정과목 |
| --- | --- | --- | --- |
| 1 | 슬립 합계 | — | **110 외상매출금** |
| 2 | — | 공급가액 | **401 상품매출** |
| 3 | — | 부가세 | **220 부가세예수금** |

> 분개는 자동으로 POSTED 상태가 됩니다. 회계 직원이 [03-회계/01. 분개 입력](../03-회계/01-분개-입력.md) (Stage 3 예정) 에서 확인 가능.

## 6. FAQ + 트러블슈팅

| 증상 | 원인 | 해결 |
| --- | --- | --- |
| [발송] 버튼이 안 보임 | SALES ROLE 미보유 또는 본인이 작성한 슬립이 아님 | MANAGER 에게 ROLE 또는 권한 위임 요청 |
| [거절] 버튼이 안 보임 | MANAGER 권한 미보유 | MASTER 에게 ROLE 변경 요청 |
| [취소] 버튼이 ACCEPTED 단계에서 안 보임 | 정상 — ACCEPTED 이후는 거절(REJECTED) 만 가능 | MANAGER 에게 거절 요청 |
| 거절 후 재발행 라인이 비어 있음 | parentSlipNo 매핑 실패 (drift) | 개발팀 문의 (slip-service V12 migration 확인) |
| 자동 분개가 생성 안됨 | accounting-service 비활성 / Eureka 미등록 | IT 관리자 문의 |
| `이미 CANCELLED 입니다` | 동일 endpoint 중복 호출 | F5 → 현재 status 재확인 |
| `이미 CONFIRMED 입니다` | 동일 — 정산 후 변경 불가 | 회계 부서에 역분개(reverse) 요청 |
| 알림이 안 옴 | P1-1 UI 미구현 | 슬립 목록 직접 새로고침 (F5) |
