> ⚠️ **구현 상태** — ✅ Backend (slip-service OUTBOUND 슬립 11 status + inventory-service `/inventory/reserve` / `/release` / `/deduct` 자동 동기 + **PR-G1: 12 신규 컬럼 + 자체 발행 일원화**) / ⏳ Frontend (legacy v4 webview + 모바일 서명 일부)
>
> 미구현 부분: P0-4 (출고전표 인쇄는 ✅, 거래명세서 ⏳, 세금계산서 ❌), 부분 출고 / 묶음 발행 (slip-service §7.4)
>
> **PR-G1 변경 (Phase 10 step-14)** — 출고전표 발행 시 거래처 전화/주소/대표자/배송지/검수지/수령자전화/입금예정/할인/결제조건/약정조건 등 12 부가 정보를 **별도 컬럼**으로 분리 보존. 이전에는 메모 1000자 안에 결합되어 검색·인쇄·보고서 활용이 어려웠음. **이카운트 외부 호출 폐기** — Samhan Public 자체 발행 (slip-service `POST /api/v1/slip-publish/from-{estimate,partner-order}`) 으로 일원화. 자세한 컬럼 안내는 §2-8 참조.

## 이 매뉴얼에서 배울 내용

1. 출고 슬립 (OUTBOUND) 처리 단계 — accept(reserve) → process → inspect → complete(deduct)
2. 재고 자동 예약 / 해제 / 차감 동작
3. 재고 부족 시 409 CONFLICT 처리
4. 출하 → 배송 → 모바일 서명 흐름
5. DeliveryBatch 묶음 발송

## 2. 단계별 처리

### 2-1. Step 1 — 접수 (SENT → ACCEPTED) + 재고 예약

대상 슬립 클릭 → **[접수]** → `POST /slips/{id}/accept`.

내부적으로 `inventory-service` `POST /inventory/reserve` 가 자동 호출되어 라인별 수량이 **예약** 됩니다.

```
[변경 전]                  [reserve 호출]              [변경 후]
HQ-001 + Samsung HVAC                                HQ-001 + Samsung HVAC
balance: 150EA           ─────────────────────→     balance: 150EA
reserved: 0EA              slip line 100EA          reserved: 100EA
available: 150EA                                    available: 50EA
```

> ⚠️ 영업이 SENT 시점에 reserve 가 이미 호출되었다면 ACCEPTED 시 중복 예약은 발생하지 않음 (idempotent).

### 2-2. 재고 부족 시 — 409 CONFLICT

예약 시 가용 재고 < 요청 수량 인 경우 :

```
HTTP/1.1 409 Conflict
{
  "code": "INVENTORY_INSUFFICIENT",
  "message": "재고가 부족합니다",
  "details": {
    "warehouseCode": "HQ-001",
    "productCode": "P-2026-0001",
    "requested": 100,
    "available": 50
  }
}
```

#### 대처 절차

1. 화면에 **빨간 토스트** + 라인 단위로 부족 수량 표시
2. 옵션 A — **부분 출고** (P0 미구현 — slip-service §7.4): 가용 재고만큼만 출고 슬립 분할 → 추후 입고 후 잔여 슬립 발행
3. 옵션 B — **임시 우회**: 영업에 슬립 거절 / 분할 발행 요청
4. 옵션 C — **재고 확보**: [01. 입고 처리](01-입고-처리.md) 로 입고 후 재시도
5. 옵션 D — 다른 창고 (`VH-001`) 에서 [03. 재고 조회](03-재고-조회.md) → 창고이동(transfer) 후 재시도

### 2-3. Step 2 — 처리 (ACCEPTED → PROCESSING)

물품 picking 시작 → [처리] → `POST /slips/{id}/process`.

### 2-4. Step 3 — 검수 (PROCESSING → INSPECTING)

라인별 picking 완료 → [검수] → `POST /slips/{id}/inspect`.

### 2-5. Step 4 — 완료 (INSPECTING → COMPLETED) + **재고 차감**

[완료] → `POST /slips/{id}/complete`.

이 시점에 `inventory-service` `POST /inventory/deduct` 가 자동 호출되어 **재고가 실제로 차감**됩니다.

```
[변경 전]                  [deduct 호출]              [변경 후]
HQ-001 + Samsung HVAC                                HQ-001 + Samsung HVAC
balance: 150EA           ─────────────────────→     balance: 50EA
reserved: 100EA            slip line 100EA          reserved: 0EA
available: 50EA                                     available: 50EA
```

> 차감 시 FIFO 우선 — 가장 오래된 lot 부터 차감 (V5 migration). lot 별 차감 수량은 movement history 에 기록.

### 2-6. Step 5 — 출하 (COMPLETED → SHIPPING)

트럭 적재 완료 → [출하] → `POST /slips/{id}/ship`.

### 2-7. Step 6 — 배송 완료 (SHIPPING → DELIVERED) + 서명 수신

기사가 거래처 도착 → 모바일 서명 수신 → [배송 완료] → `POST /slips/{id}/deliver`.

> 모바일 서명은 별도 흐름 — DeliveryBatch + share token (§3 참조).

## 2-8. 신규 입력 항목 (Phase 10 step-14, PR-G1)

이전 분석 (e-Count BulkDatas 14 필드 vs Samhan Public schema 비교) 결과, 기존에 메모 1000자에 결합되어 있던 12 필드를 별도 컬럼으로 분리합니다. 운영 측면에서 검색·인쇄 양식·보고서 활용 가능합니다.

### 2-8-1. 12 신규 컬럼 일람

| # | 컬럼 | 한국어 라벨 | 유형 | 입력 시점 | 자동/수동 |
| ---: | --- | --- | --- | --- | --- |
| 1 | `IO_TYPE` | 입출고 구분 | `String(2)` | 슬립 발행 | 자동 (출고 = `10`) |
| 2 | `TIME_DATE` | 처리 시각 (분 단위) | `LocalDateTime` | 슬립 발행 | 자동 |
| 3 | `customer_tel` | 거래처 전화 snapshot | `String(20)` | 슬립 발행 | 자동 (partner snapshot) |
| 4 | `customer_addr` | 거래처 주소 snapshot | `String(255)` | 슬립 발행 | 자동 (partner snapshot) |
| 5 | `customer_rep` | 거래처 대표자 snapshot | `String(50)` | 슬립 발행 | 자동 (partner snapshot) |
| 6 | `shipping_addr` | 배송지 (거래처 주소와 다를 때) | `String(255)` | 영업 입력 | 수동 (DRAFT/SAVED 단계) |
| 7 | `inspection_addr` | 검수지 (거래처 도착 후 검수 위치) | `String(255)` | 영업 입력 | 수동 |
| 8 | `receiver_phone` | 수령자 전화 (거래처 직원 외 별도 인수자) | `String(20)` | 영업 입력 | 수동 |
| 9 | `payment_due` | 입금 예정일 (`MM-DD`) | `String(5)` | 영업 입력 (거래처 수금예정일 자동 채움 후 수정 가능) | 자동 + 수정 |
| 10 | `discount_info` | 할인 정보 (DC 적용 내역) | `String(255)` | 영업 입력 | 수동 |
| 11 | `collect_term` | 결제 조건 (외상/현금/분할/어음) | `String(100)` | 영업 입력 (거래처 마스터 자동 채움 후 수정 가능) | 자동 + 수정 |
| 12 | `agree_term` | 약정 조건 (반품/교환/보증) | `String(255)` | 영업 입력 | 수동 |

### 2-8-2. 거래처 snapshot (`customer_tel` / `customer_addr` / `customer_rep`)

거래처 마스터의 전화·주소·대표자가 **나중에 변경**되어도 본 슬립은 발행 시점 값을 그대로 보존합니다. 출고전표 인쇄 / 거래명세서 / 세금계산서 / 보고서 모두 발행 시점 값으로 출력됩니다.

> **운영 의미** — 거래처가 이사하거나 대표자가 바뀌어도 과거 출고 이력의 거래 상대 정보가 정확히 추적됩니다. 분쟁 / 감사 시점에 발행 당시 거래 사실 보존 (한국 일반기업회계기준 거래 보존 원칙 준수).

### 2-8-3. 배송지 / 검수지 / 수령자 전화 (`shipping_addr` / `inspection_addr` / `receiver_phone`)

거래처 주소와 **다른 배송지** 가 있는 경우에 입력합니다.

| 시나리오 | 입력 예시 |
| --- | --- |
| 거래처는 본사 주소이지만 배송은 거래처의 다른 현장으로 | `shipping_addr` = `서울 강남구 테헤란로 123 현장 사무소` |
| 거래처 도착 후 거래처 검수실에서 검수 | `inspection_addr` = `서울 강남구 테헤란로 123 3층 검수실` |
| 거래처 사장님이 아닌 현장 책임자가 수령 | `receiver_phone` = `010-9876-5432` (현장 책임자) |

> **모바일 서명과의 연계** — `receiver_phone` 이 입력되면 DeliveryBatch SMS 발송 시 거래처 마스터 전화 대신 본 번호로 share token URL 발송. 즉 **현장 인수자가 직접 모바일 서명** 가능.

### 2-8-4. 결제 정보 4 컬럼 (`payment_due` / `discount_info` / `collect_term` / `agree_term`)

이전 메모 결합 형태 (예: `메모: 결제 6/30 외상 / DC 5% / 반품 30일`) 가 4 개의 별도 컬럼으로 분리됩니다.

| 컬럼 | 입력 예시 |
| --- | --- |
| `payment_due` | `06-30` (6월 30일 입금 예정) |
| `discount_info` | `홈쇼핑 5% DC` 또는 `라인별 -10%` |
| `collect_term` | `30일 어음`, `현금 즉시`, `월말 마감 익월 30일` |
| `agree_term` | `반품 30일 보장`, `불량 무상 교환`, `설치 포함` |

> **자동 채움 + 수정** — `payment_due` / `collect_term` 은 거래처 마스터의 수금예정일 / 결제조건 정책에서 자동 채움. 슬립별 예외 시 영업이 수정 (DRAFT/SAVED 단계에서만).

### 2-8-5. 운영 변경 안내 (이전 vs 변경)

| 측면 | 이전 (V12 이전) | 변경 (V16 PR-G1) |
| --- | --- | --- |
| 부가 정보 저장 | 메모 1000자 안에 모든 정보 결합 | 12 별도 컬럼 분리 |
| 검색 가능성 | 메모 LIKE 부분 일치만 | 컬럼별 인덱스 검색 가능 (예: `payment_due BETWEEN '06-01' AND '06-30'`) |
| 인쇄 양식 활용 | 메모 통째로 출력 (구조화 어려움) | 컬럼별 라벨 인쇄 (거래명세서 양식 정합성) |
| 보고서 집계 | 불가 (메모 텍스트) | DC 합계 / 결제 조건별 매출 집계 가능 |
| **이카운트 외부 호출** | BulkDatas 양식 호환 외부 API 호출 | **폐기** — Samhan Public 자체 발행 (`POST /api/v1/slip-publish/from-{estimate,partner-order}`) 으로 일원화 |

> **이카운트 외부 호출 폐기 의미** — 사용자 명시 결정. 이전에는 이카운트 ERP 의 `BulkDatas` 양식 호환을 위해 슬립 발행 시 외부 API 호출이 함께 일어났습니다. PR-G1 머지 후 외부 호출 코드 제거 + 자체 분개 (PR #118 accounting-service native 이식 완성) + 출고전표 자동 조회 (PR #117 slip-service 5 endpoint) 로 100% 자체 발행. 이카운트 양식 reference 캡처 (`docs/migration/ecount-reference/`) 는 schema 호환 보존용으로만 유지.

### 2-8-6. 입력 절차

1. **영업이 출고 슬립 발행 시** ([01-영업/03. 슬립 발행](../01-영업/03-슬립-발행.md)) — 헤더 입력 화면에 12 컬럼 자동 채움 + 수정 가능
2. **창고 접수 시** — 12 컬럼 read-only 표시 (출고 처리 절차에 영향 없음, 정보 활용만)
3. **검수 시** — `shipping_addr` 와 실 배송지 대조 / `inspection_addr` 와 실 검수 위치 대조
4. **출하 / 배송 / 모바일 서명** — `receiver_phone` 으로 SMS share token 발송 (입력 시) → 현장 인수자 직접 서명

> **이전 운영 방식과의 호환** — V12 이전 슬립은 12 컬럼 모두 `NULL`. 정상 동작 (legacy 호환). PR-G1 후 신규 슬립부터 자동 채움.

## 2-9. 수정 이력 보기 (Phase 12 step-2, PR-H2)

> **PR-H2 변경** — 슬립의 모든 필드(메모/배송지/검수지/수령자전화/결제정보/품목 수량 등)는 변경될 때마다 audit log 가 누적되며, 화면에서 "취소선 + 수정자 색상 + 수정자 이름" overlay 로 한눈에 확인할 수 있습니다.

### 2-9-1. 수정 횟수 카운트 (슬립 헤더)

슬립 상세 화면 우측 상단에 **수정 N회** badge 가 표시됩니다.

```
[슬립번호] 2026-05-09-001       [상태: 승인대기]   수정 5회
```

| 횟수 | 색상 | 의미 |
| ---: | --- | --- |
| 0회 | (badge 숨김) | 신규 작성 후 수정 없음 |
| 1~4회 | 회색 | 정상 범위 |
| 5~9회 | 노랑 | 다중 수정 주의 환기 |
| 10회+ | 빨강 | 비정상적 다수 수정 — 검토 권장 |

### 2-9-2. 필드별 audit overlay

각 필드 우측에 가장 최근 변경이 inline 으로 표시됩니다.

```
메모  긴급 출고 요청 (오늘 마감 전)   ~~오전 배송 부탁드립니다~~   ● 김영업 14:32
```

읽는 법:

| 시각 요소 | 의미 |
| --- | --- |
| 검정 굵은 텍스트 | 현재 값 |
| 취소선 + 회색 텍스트 | 변경 직전 값 (가장 최근 1건) |
| ● 색상 dot | 수정자 식별 색상 (동일 사용자는 항상 같은 색) |
| 수정자 이름 | 풀네임 (UUID 비공개) |
| `HH:mm` | 변경 시각 (오늘 = 시각만, 어제 이전 = `MM-DD HH:mm`) |

> **색상 정책** — 색상은 사용자 ID 의 deterministic hash 로 자동 결정됩니다. 동일 사용자는 슬립이 달라져도 같은 색상이 유지되므로, "이 색은 김영업" "저 색은 박관리" 식으로 시각 학습이 가능합니다. (`userIdToColor` HSL hash, PR-H1 시드)

### 2-9-3. 다중 revision 펼치기

같은 필드가 2회 이상 수정되었다면 inline 아래에 **[이력 N개 보기]** 버튼이 표시됩니다.

```
메모  익일 오전 배송으로 확정   ~~오후 배송으로 변경 요청~~   ● 박관리 16:48

[이력 3개 보기]   ◀ 클릭
```

클릭하면 가장 최근 → 과거 순으로 전체 revision 이 펼쳐집니다.

```
[이력 닫기]
  ┌───────────────────────────────────────────────────────┐
  │ ~~오전 배송 부탁드립니다~~              ● 김영업 14:32 │
  │ ~~(빈 값)~~                            ● 이작성 11:05 │
  └───────────────────────────────────────────────────────┘
```

> 빈 값 (NULL → 신규 입력) 은 `(빈 값)` 으로 가시화됩니다.

### 2-9-4. 복원 (MANAGER + MASTER 권한)

각 revision 우측의 **▾** 드롭다운에서 해당 시점 값으로 복원할 수 있습니다.

```
~~오후 배송으로 변경 요청~~   ● 박관리 16:48 ▾
                                       │
                                       ↓ 클릭
                          ┌────────────────────────┐
                          │ ↩ 이 시점으로 복원     │  ← rev 4 = 현재
                          │ ↩ rev 3 으로 복원      │
                          │ ↩ rev 2 으로 복원      │
                          │ ↩ 최초 값으로 복원     │
                          └────────────────────────┘
```

| 권한 | 복원 가능? |
| --- | --- |
| MASTER | ✅ |
| MANAGER | ✅ |
| WAREHOUSE / INVENTORY / SALES / DRIVER / ACCOUNTING | ❌ (드롭다운 자체 hide) |

복원 절차:

1. 드롭다운에서 복원할 revision 클릭
2. 확인 다이얼로그 — `revision N 으로 복원하시겠습니까?`
3. 확인 → 새 revision 이 추가됩니다 (이전 revision 은 삭제되지 않고 audit log 에 그대로 보존)
4. 슬립 헤더 "수정 N회" 카운트 +1 증가

> **복원 = 새 revision 추가** — 기존 revision 은 절대 삭제되지 않습니다. 한국 일반기업회계기준의 거래 보존 원칙에 따라 모든 수정 흔적이 audit log 에 영구 기록됩니다.

### 2-9-5. UUID 비공개 가드

화면 어디에도 사용자 UUID 가 직접 노출되지 않습니다.

- 화면 표시: 풀네임 (`김영업`, `박관리`)
- 색상 식별: dot 색상 (`userIdToColor(userId)` hash 결과)
- DOM `data-testid` / `aria-label` 등 속성에도 UUID 노출 금지

### 2-9-6. 운영 변경 안내 (이전 vs PR-H2 변경)

| 측면 | 이전 (PR-H2 이전) | 변경 (PR-H2) |
| --- | --- | --- |
| 수정 흔적 | 마지막 수정자/시각만 (단일 컬럼) | 모든 revision 이력 audit log 누적 |
| 화면 표시 | 별도 화면 진입 ("이력 보기" 별도 메뉴) | 슬립 상세 화면에 inline overlay (취소선 + 색상) |
| 수정자 식별 | 텍스트 풀네임만 | 풀네임 + 색상 dot (시각 학습 가능) |
| 복원 | 불가 (수동 재입력만) | MANAGER + MASTER 권한 시 드롭다운 복원 |

### 2-9-7. FAQ — 수정 이력

| 증상 | 원인 | 해결 |
| --- | --- | --- |
| "수정 N회" badge 가 안 보임 | 수정 횟수 0회 (신규 작성 후 변경 없음) | 정상 동작 — 0회는 의도적 hide |

## 2-10. 수정 / 삭제 요청 워크플로우 (Phase 12 step-3, PR-H3)

> **PR-H3 변경** — 슬립이 일정 단계 이후로 진행되면 수정·삭제가 자동 잠금됩니다. 정당한 사유가 있을 때 권한자(MANAGER+/MASTER)에게 명시적 요청 → 수락 시 임시 unlock → 수정 후 자동 재잠금. 모든 요청/수락/거절은 PR-H2 audit log 에 영구 누적됩니다.

### 2-10-1. 잠금 단계 4분류

| 잠금 단계 | 적용 status | 수정 경로 | unlock 시간 |
| --- | --- | --- | --- |
| **0차 (잠금 없음)** | `DRAFT` / `SAVED` | 본인 + MANAGER+ 즉시 수정 | (잠금 없음) |
| **1차 잠금** | `SENT` / `ACCEPTED` / `PROCESSING` / `REJECTED` | 본인 → 권한자 요청 → MANAGER 수락 | 24시간 |
| **2차 잠금 (사유 200자 필수)** | `INSPECTING` / `COMPLETED` / `SHIPPING` / `DELIVERED` | 본인 → 권한자 요청 → MASTER 수락 | 1시간 |
| **영구 잠금** | `CONFIRMED` / `CANCELED` | 회계 역분개 또는 신규 슬립 발행 | (수정 불가) |

> ⚠️ 출고 단계 중 `INSPECTING`/`SHIPPING`/`DELIVERED` 는 모두 2차 잠금에 해당. 검수 또는 배송 도중 슬립 변경이 필요한 경우 사유 200자 이상 + 비즈니스 카테고리 (거래처 요청 / 재고 차질 / 법적 사유 / 기타) 선택 필수입니다.

### 2-10-2. 1차 잠금 — 수정 요청 절차

대상 status: `SENT`, `ACCEPTED`, `PROCESSING`, `REJECTED`.

```
[본인 영업: 김영업]                  [MANAGER: 박관리]
  슬립 상세 → [✏ 수정 요청]
       ↓
  SlipEditRequestDialog
   - 사유 입력 (50자 권장)
   - 수정 항목 체크 (메모/품목/배송지/...)
   - [요청 보내기]                  → 알림 토스트:
                                      "김영업이 슬립 #001 수정 요청"
                                      ↓
                                    [수정 요청 검토] 다이얼로그
                                     - 사유 검토
                                     - 검토 의견 입력 (선택)
                                     - [수락] / [거절]
       ↑                                  ↓
       알림: "수정 요청이 수락되었습니다 (24시간 내 수정 가능)"
       ↓
  슬립 상세 → 노란 banner: "수정 가능 23:48 남음"
       ↓
  필드 자유 편집 → [저장] → 자동 재잠금 + audit log 누적
```

| 단계 | 화면 | 비고 |
| --- | --- | --- |
| 1. 요청 | `[✏ 수정 요청]` 버튼 (슬립 상세 헤더) | 1차 잠금 status 에서만 노출 |
| 2. 다이얼로그 입력 | 사유 (50자 권장) + 수정 항목 체크 | 사유 빈 값 → 요청 불가 |
| 3. 수락자 알림 | MANAGER 화면 우측 상단 토스트 + 슬립 헤더 `수정 요청 검토 중` badge | 실시간 SSE push |
| 4. 검토 다이얼로그 | MANAGER 가 슬립 상세 → 토스트 클릭 → 검토 다이얼로그 | 사유 / 항목 / 검토 의견 |
| 5. 수락 → unlock | 본인 영업 화면 노란 banner: `수정 가능 23:48 남음` | 24시간 카운트다운 |
| 6. 수정 → 저장 | 모든 필드 자유 편집 → [저장] | PR-H2 audit log 자동 누적 |
| 7. 자동 잠금 | 저장 시 즉시 잠금 / 또는 24h 만료 시 자동 잠금 | banner 회색 "잠금 복귀" |

### 2-10-3. 2차 잠금 — 검수/배송 단계 수정 요청 (사유 200자)

대상 status: `INSPECTING`, `COMPLETED`, `SHIPPING`, `DELIVERED`.

1차 잠금과 다른 점:

| 항목 | 1차 | 2차 |
| --- | --- | --- |
| 사유 글자 수 | 50자 권장 | **200자 이상 강제** |
| 비즈니스 카테고리 | 없음 | **거래처 요청 / 재고 차질 / 법적 사유 / 기타** 4 옵션 중 1개 필수 |
| 수락자 | MANAGER (즉시 수락) | MASTER (MANAGER 는 검토 의견만 첨부 가능) |
| unlock 시간 | 24시간 | **1시간** (긴급 처리 강제) |
| audit log | 누적 | **영구 보존 + 감사 표시** |
| banner 색상 | 노랑 | 빨강 (위험 강조) |

> **운영 의미** — 검수 중에 거래처가 수량 변경을 요청하는 일이 흔하지만 이미 재고 예약(reserve)이 진행되었기에 함부로 변경하면 회계/재고 정합성 위험. 2차 잠금은 이 위험을 명시화하여 MASTER 의 결재가 필수임을 강제합니다.

### 2-10-4. 삭제 요청 절차

대상 status: `DRAFT`/`SAVED` 외 모든 단계 (DRAFT/SAVED 는 본인이 즉시 삭제 가능).

```
[본인 영업]                          [MANAGER+ / MASTER]
  슬립 상세 → [⌫ 삭제 요청]
       ↓
  SlipDeleteRequestDialog
   - 사유 입력 (필수)
   - "삭제 = soft delete + CANCELED status"
   - [요청 보내기]                  → [수락] → 즉시 삭제
                                      ↓
                                    슬립 status = CANCELED
                                    deleted_at = now()
                                    audit log 영구 보존
       ↑
       알림: "슬립이 삭제되었습니다.
              관련 분개는 회계팀에 통보됨"
```

| 단계 | 비고 |
| --- | --- |
| `DRAFT`/`SAVED` 단계 | 본인 즉시 삭제 (요청 절차 없음) |
| `SENT`~`DELIVERED` | MANAGER+ 요청 수락 후 삭제 |
| `CONFIRMED` | 삭제 불가 — 회계 역분개 절차로만 처리 |
| `CANCELED` | 이미 취소됨 — 신규 슬립 발행으로 대체 |

> **삭제 방식** — soft delete (`deleted_at` 컬럼 set + 화면 hide). audit log 는 영구 보존되어 감사 시점 추적 가능. 회계 분개가 있다면 (CONFIRMED 후) 자동 역분개 큐에 등록 (accounting-service 연동 — 후속 PR).

## 3. DeliveryBatch — 묶음 발송 + 모바일 서명

여러 슬립을 같은 기사에게 묶어 SMS 1건 발송.

### 3-1. 자동 grouping

slip 목록 화면 → [☰ 자동 grouping] → `POST /delivery-batches/auto-group` → `driverPhone` 별로 batch 생성.

### 3-2. 기사 SMS 발송

batch 상세 → [SMS 발송] → `POST /delivery-batches/{id}/send-sms`.

기사 핸드폰에 share token URL 수신:
```
[Samhan Public] 오늘 배송 3건 (강남/송파/관악)
https://app.samhan-air.com/m/batch/abc123def456
```

### 3-3. 기사 모바일 서명

기사가 URL 클릭 → 거래처 도착 → 거래처 직원 서명 + 본인 (DRIVER) 서명 → 자동으로 슬립 DELIVERED 전이.

> 자세한 모바일 서명: Stage 3 [04-모바일/02. 전자 서명](../04-모바일/02-전자-서명.md) (예정).

## 5. 출고 취소 / 거절

### 5-1. ACCEPTED 이전 — 영업 취소 가능

영업 직원이 [01-영업/04. 슬립 결재 라인](../01-영업/04-슬립-결재-라인.md) §4 절차로 취소 (CANCELLED). 이 경우 reserve 가 자동 release.

### 5-2. ACCEPTED 이후 — MANAGER 거절만 가능

검수 시 발견된 문제 (재고 손상 / 거래처 변경 등) → MANAGER 에게 거절 요청 → `POST /slips/{id}/reject` (사유 필수).

거절 시 reserve 자동 release. 차감 (deduct) 후 거절은 회계 직원의 역분개 (reverse) 필요.

| 묶음 발행이 안됨 | UI 미구현 (slip-service §7.4) | 단건 발행 반복 |
| DeliveryBatch SMS 가 안 옴 | `AligoSmsGateway` 미설정 (P1-1) | share token URL 복사 후 카카오톡 직접 전송 |
| 기사 서명 후에도 DELIVERED 안 됨 | token 만료 / 서명 저장 실패 | `POST /delivery-batches/{id}/regenerate-token` 으로 재발행 |
| 출고전표 인쇄 시 한글 깨짐 | 폰트 미설치 | Noto Sans KR 시스템 설치 |
| 거래명세서 출력이 이상함 | P0-4 부분 구현 (legacy v4 일부) | 정식 양식 fix 대기 |
| 거래처 주소가 바뀌었는데 과거 슬립이 변경됨? | snapshot 미적용 (V12 이전 슬립) | PR-G1 후 신규 슬립은 발행 시점 보존. 과거 슬립은 customer_addr=NULL 표시 |
| `payment_due` 자동 채움이 안 됨 | 거래처 마스터 수금예정일 미입력 | [01-영업/01. 거래처 등록](../01-영역/01-거래처-등록.md) 의 여신/단가 탭 (P0-6) 에서 수금예정일 등록 필요 |
| 이카운트 양식으로 export 가능? | 외부 API 호출 폐기 (PR-G1) | Samhan Public 자체 발행으로 일원화. 거래명세서 / 세금계산서 자체 양식 사용 (P0-4 진행 중) |
| `receiver_phone` SMS 발송 안 됨 | 입력 누락 → 거래처 마스터 전화로 fallback | 영업이 슬립 발행 시 현장 인수자 전화 입력 |
