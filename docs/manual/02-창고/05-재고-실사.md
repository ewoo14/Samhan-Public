## 1. 재고 실사 (Cycle Count) 정의

### 1-1. 무엇이 재고 실사인가?

- 정기적 (월 1회 / 분기 1회) 으로 **창고 실물 재고** 와 **시스템 재고** 의 일치 검증
- 차이 발견 시 = 분실 / 도난 / 입출고 누락 / 시스템 버그 가능성
- 한국 회계 표준 — 매년 1회 의무 (12월말 또는 회계 연도말)

### 1-2. 실사 방식 분류

| 방식 | 빈도 | 대상 |
| --- | --- | --- |
| 전수 실사 (full count) | 월 1회 또는 연 1회 | 모든 제품 |
| 순환 실사 (cycle count) | 매주 / 매일 | 일부 제품 (loop) |
| 무작위 실사 (random count) | 비정기 | 소수 무작위 제품 |
| ABC 실사 | 분기 | A 등급 (고가) 매월 / B 매분기 / C 연 1회 |

본 시스템 정식 fix 시 = 순환 실사 + 전수 실사 지원 권고.

## 3. 임시 우회 (현재 운영 절차)

### 3-1. 수동 실사 (회계 + 창고 + 영업 합동)

1. **사전 준비**
   - 회계 직원이 시스템 재고 리포트 출력 — `/inventory/balances?warehouseCode=HQ-001`
   - Excel template (창고 표준) 에 시스템 재고 column 채움

2. **실사 일자 결정 (보통 월말 17:00 ~ 익일 09:00)**
   - 실사 시간대 동안 모든 출고 / 입고 차단 (영업 / 창고 협조)
   - 실사 시작 시각 = 시스템 재고 snapshot

3. **창고 작업자 실물 카운트**
   - 창고 작업자 2명 1조 (cross-check)
   - 제품별 실물 수량 Excel 에 기록
   - 차이 발견 시 → 사유 메모 (분실 / 파손 / 미출고 등)

4. **회계 직원 차이 정리**
   - 시스템 vs 실물 차이 = Excel 자동 계산
   - 차이 합계 = 분개 (조정 분개 — 손실 / 이익)
   - MANAGER 결재

5. **시스템 재고 보정**
   - 차이 만큼 inventory-service `/inventory/adjust` 직접 호출 (개발팀 우회 — UI 부재)
   - 또는 개발팀에 SQL 요청 (`UPDATE inventory_balance SET quantity = ...`)

### 3-2. 실사 우회의 위험

- 실사 시간대 동안 출고 차단 → 영업 / 창고 운영 1박 2일 정지
- 모바일 바코드 스캔 부재 → 실수 위험 (특히 같은 모델 다른 lot)
- 차이 사유 audit 부재 → 회계 책임 소재 불명확
- 시스템 보정 = 개발팀 SQL → audit log 손실

## 4. 정식 fix 계획 (Stage 4 — P2-6)

### 4-1. P2-6 PR 권고 범위

```
1. inventory-service:
   - InventoryCount 도메인 (마스터 + 라인)
   - 실사 status workflow: DRAFT → IN_PROGRESS → COMPLETED → ADJUSTED
   - 차이 자동 계산 endpoint (`GET /inventory/counts/{id}/variances`)

2. accounting-service:
   - 실사 차이 → 조정 분개 자동 생성 (`POST /accounting/journals/from-count`)
   - 손실 (재고 차감) / 이익 (재고 증가) 분류

3. mobile-staff:
   - 바코드 스캔 화면 (Expo Camera + ZXing)
   - 실시간 실물 카운트 입력
   - 차이 즉시 표시 (시스템 vs 실물)

4. desktop UI:
   - [재고 실사] 메뉴 (사이드바 → 창고 → 실사)
   - 실사 마스터 등록 (날짜 / 창고 / 담당자)
   - 실사 진행 화면 (라인별 시스템 vs 실물 + 사유 입력)
   - 차이 리포트 + MANAGER 결재 + 자동 조정 분개

5. notification-service:
   - 실사 시작 / 완료 알림 (해당 창고 직원 push)
```

## 7-1. 수정 이력 보기 (Phase 12 step-4c, PR-H4c FE rollout)

> **PR-H4c 변경** — P2-6 fix 후 정식 StockCountPage 도입 시 본 절의 audit overlay + DRAFT 자유 수정 + POSTED FULLY_LOCKED 정책이 자동 적용됩니다. 본 절은 시드 패턴 (PR-H2 `02-출고-처리.md` § 2-9) 의 재고 실사 도메인 적용 — slip 화면과 시각 1:1 동일.

### 7-1-1. 실사 헤더 "수정 N회" badge

StockCountPage 우측 상단에 **수정 N회** badge 표시 (시드 임계 색상).

### 7-1-2. 필드별 audit overlay (실사 차이 / 사유)

각 라인 우측에 가장 최근 변경:

```
시스템 재고       12 EA                (시드)
실측 수량         9 EA                 ~~10 EA~~          ● 김창고 13:32 (재카운트)
차이              -3 EA                ~~-2 EA~~          ● 김창고 13:32
사유              파손 발견             ~~검수 누락~~       ● 박관리 13:32 (확인 후 수정)
```

### 7-1-3. DRAFT/IN_PROGRESS 자유 수정 (실사 진행 중)

실사 status 가 `DRAFT` 또는 `IN_PROGRESS` (실측 진행) 인 경우 자유 수정 — WAREHOUSE / INVENTORY / MANAGER 모두 가능.

### 7-1-4. COMPLETED LOCKED_REQUIRES_APPROVAL (결재 대기)

`COMPLETED` (결재 대기) 상태 = LOCKED_REQUIRES_APPROVAL — MANAGER 승인 후 1회 한정 mutation.

```
[잠금 banner]
이 실사는 잠금 상태입니다 — 수정 요청을 보내주세요.
결재 대기 단계 = 회계 전기 직전. 변경 시 권한자 (MANAGER / MASTER) 승인 필요.

[+ 수정 요청]
```

### 7-1-5. ADJUSTED FULLY_LOCKED (조정 분개 완료)

`ADJUSTED` (조정 분개 완료) 후에는 직접 수정 불가:

```
[잠금 banner]
이 실사는 완전 잠금 상태입니다 — MASTER 에게 문의하세요.
조정 분개 완료 — 한국 일반기업회계기준 보존 의무 (별도 정정 분개 절차).
```

### 7-1-6. 1초 SSE 실시간 sync (multi-context — 다수 창고원 동시 실사)

WAREHOUSE 2명 1조가 cross-check 하는 경우 두 디바이스 (모바일 + desktop) 가 1초 안에 동기화 — 동일 라인 충돌 방지.

```
[우측 상단 toast]
실시간 변경 감지 — 0.8초
김창고 님이 실측 수량 을 "9 EA" 으로 수정했습니다. (rev #2 — 재카운트)
```

### 7-1-7. 한국 회계 무결성 표기 (조정 분개 자동 트리거)

차이 사유 + 조정 금액이 자동 분개로 전기되는 시점에 안내 banner:

```
[안내 banner]
실사 차이 -3 EA × 단가 12,000원 = 36,000원 손실 → 조정 분개 자동 생성됩니다.
차변 매출원가 / 대변 재고 — POSTED 후에는 정정 분개 절차로만 수정 가능합니다.
```
