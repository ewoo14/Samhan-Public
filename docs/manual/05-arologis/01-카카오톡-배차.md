## 1. 카카오톡 배차 메시지 표준 형식

본 시스템 파서는 다음 형식 기반으로 80% 이상 자동 파싱합니다. **형식 준수가 정확도의 가장 큰 변수**.

```
8일착 야상입니다
1. 상일+초월
-인천 남동구 구월동(에스엠하나공조-214)아침8시
-인천남동구논현동755-1(하늘시스템-218)9시하차
1톤

2. -경기 김포시 고촌읍(삼공주에어컨-17)오전일찍
-경기 부천시 원미구(시원에어컨-99)10시
2.5톤

13. 상일상차
-경기 광주시 곤지암읍(코스모냉동-301)오후
5톤
```

### 1-1. 헤더 라인

`(N)일착 (TYPE)입니다` 형식. 예: `8일착 야상입니다`.

| 단어 | 의미 |
| --- | --- |
| **8일착** | 도착일 — 입력 시점 기준 가까운 월/년 자동 추론 (오늘 5/7 → 8 = 5/8) |
| **야상** | DispatchType.NIGHT (야간배송) — `야상` / `야간` |
| **주간** | DispatchType.DAY (주간배송) — `주간` 또는 미지정 시 default |
| **특급** | DispatchType.EXPRESS — `특급` / `긴급` / `EXPRESS` |

### 1-2. 차량 헤더 라인

`(N). (label)` 형식. 예: `1. 상일+초월` / `2.` (label 없음) / `13. 상일상차`.

- `N` = 차량 sequence (1~99)
- `label` = 차량 그룹 별명 (선택). 첫 정차가 같은 라인에 오는 경우 (`2. -경기...`) 도 자동 처리

### 1-3. 톤수 라인

`(숫자)톤` 형식. 차량 그룹의 끝에 위치. 예: `1톤` / `2.5톤` / `1.4톤`.

> ⚠️ 톤수 라인이 없는 차량은 default `1톤` 으로 저장 — 운영자가 수동 보정 필요 (P1-5 UI 도착 시).

### 1-4. 정차 라인

`-(주소)((사업자명)-(슬립번호))(특이사항)` 형식.

```
-인천 남동구 구월동(에스엠하나공조-214)아침8시
   ↑ 주소               ↑ 사업자       ↑ 슬립번호  ↑ 특이사항
```

| 추출 필드 | 예 | 사용처 |
| --- | --- | --- |
| 주소 | `인천 남동구 구월동` | 지도 표시 / GPS 라우팅 |
| partnerName | `에스엠하나공조` | 거래처 매칭 (P1-5 자동 score) |
| partnerCode | `214` | slip-service 슬립번호 lookup (W10-4 SlipResolver) |
| notes | `아침8시` | 도착 시각 / 특이사항 메모 |

### 1-5. 미해석 라인

위 패턴 어디에도 매칭되지 않는 라인 (예: `상일상차` / `초월하차`) 은 `status=UNPARSED` 로 보존. 운영자가 admin UI 에서 수동 보정 가능 (P1-5 도착 후).

## 2. 운영 흐름 (현재 W10-1 시점)

```
[배차 담당]                          [Samhan Public arologis]
카톡 메시지 복사 ────→ POST /admin/arologis/dispatches/parse-kakao
                          │
                          ↓ 미리보기 응답 (저장 X)
                       ParsedDispatch
                       { dispatchDate, type,
                         vehicles: [{seq, tonnage, label,
                                     stops: [...]}],
                         totalLines, parsedLines }
                          │
                          ↓ (검토 후)
                    POST /admin/arologis/dispatches
                          │
                          ↓
                       Dispatch 저장 + Vehicle / VehicleStop 일괄 INSERT
                          │
                          ↓ (선택)
                    POST /admin/arologis/dispatches/{id}/auto-match
                          │
                          ↓
                       활성 DriverMatcher 호출 (Mock or Insung)
                          │
                          ↓ 매칭 성공 시
                       Vehicle.assignDriver + Push 알림
```

> ⚠️ **현재 P1-5 미구현** — admin 화면이 부재합니다. 본 PR (Stage 3) 시점에서는 backend API 직접 호출 (Postman / curl) 또는 개발팀 우회 필요. Phase 11 진입 전 admin Vue/React UI 1 PR 권고.

## 3. 단계별 절차 (UI 도착 후 — P1-5 fix 시)

### 3-1. Step 1 — 카카오톡 메시지 복사

배차 단톡방에서 메시지 우클릭 → [복사].

![카카오톡 단톡방 메시지 복사](../screenshots/05-arologis/01-kakao-copy.png)

### 3-2. Step 2 — admin 화면 진입

좌측 사이드바 → [arologis] → [카카오톡 배차] (P1-5 미구현 — UI 도착 시).

![admin 카카오톡 배차 진입](../screenshots/05-arologis/01-admin-menu.png)

### 3-3. Step 3 — 메시지 붙여넣기 + 미리보기

textarea 에 붙여넣기 → [미리보기 파싱] 클릭 → `POST /admin/arologis/dispatches/parse-kakao` 호출 → 응답을 표 형태로 표시.

![파싱 미리보기 결과](../screenshots/05-arologis/01-parse-preview.png)

응답 예시:
```json
{
  "success": true,
  "data": {
    "dispatchDate": "2026-05-08",
    "dispatchType": "NIGHT",
    "totalLines": 47,
    "parsedLines": 41,
    "accuracy": 0.872,
    "vehicles": [
      {
        "sequence": 1,
        "tonnage": "TONNAGE_1",
        "label": "상일+초월",
        "stops": [
          {
            "sequence": 1,
            "rawText": "-인천 남동구 구월동(에스엠하나공조-214)아침8시",
            "parsedAddress": "인천 남동구 구월동",
            "parsedPartnerName": "에스엠하나공조",
            "parsedPartnerCode": 214,
            "notes": "아침8시",
            "unparsed": false
          }
        ]
      }
    ]
  }
}
```

### 3-4. Step 4 — 미해석 라인 수동 보정 (P1-5 도착 후)

`unparsed: true` 정차 라인은 빨강색으로 표시. 클릭 → 주소 / 거래처 / 슬립번호 직접 입력.

### 3-5. Step 5 — Dispatch 저장

[저장] 클릭 → `POST /admin/arologis/dispatches` 호출 → `{ "dispatchId": "..." }` 응답.

### 3-6. Step 6 — 자동 매칭 (선택)

[자동 매칭] 클릭 → `POST /admin/arologis/dispatches/{id}/auto-match` 호출.

활성 DriverMatcher (default `MockDriverMatcher`, 추후 `InsungQuickDriverMatcher` 활성) 가 차량마다 driver 후보를 score 로 매칭. 응답:
```json
{ "totalVehicles": 13, "matched": 9 }
```

매칭 성공한 vehicle 은 자동으로 driver 의 어플에 push 알림 송신 (`NotificationClient.send`).

## 4. 정확도 80% 미만 시

### 4-1. 원인 진단 — `parsedLines / totalLines`

응답의 `accuracy` (= `parsedLines / totalLines`) 가 0.8 미만이면 카카오톡 메시지 형식 오류 가능성. 원인:

| 증상 | 원인 | 해결 |
| --- | --- | --- |
| 헤더 미인식 (전체 파싱 실패 — 400) | `8일착 야상입니다` 형식 누락 | 메시지 첫 줄에 헤더 추가 |
| 차량 헤더 미인식 (`1.` 누락) | `1.` / `2.` numbered list 누락 | 직접 `1.` `2.` 추가 |
| 톤수 라인 누락 → 모두 1톤 | `1톤` `2.5톤` 표기 누락 | 차량 그룹 끝에 톤수 추가 |
| 정차 라인 미인식 | `-(주소)((거래처명)-(번호))` 형식 미준수 | 괄호 / 하이픈 / 사업자명 형식 정정 |

### 4-2. 단톡방 발송자에게 형식 표준화 요청

배차 책임자 (보통 영업총괄) 에게 §1 표준 형식 안내. Phase 11 후 카카오톡 봇 자동 표준화 검토 (P3 backlog).

## 5. 자동 거래처 / 슬립 매칭 (W10-4 SlipResolver)

`parsedPartnerCode` (예: `214`) 는 slip-service 의 슬립번호 (`S-2026-00214`) 로 자동 매칭됩니다.

매칭 성공 시:
- 기사 모바일 서명 시 slip-service `signatures` 테이블에도 자동 저장 (W10-4 양쪽 저장 패턴, `slipBridged: true`)
- 매칭 실패 시 arologis `signatures` 만 저장 (graceful skip)

자세한 흐름: `services/arologis-service/src/main/java/com/samhanair/logis/arologis/service/SlipResolver.java` 참조.

## 6. 자동 매칭 (DriverMatcher) 동작

### 6-1. 활성 matcher 선택

`application.yml` 의 `app.arologis.matcher.active` 설정에 따라:

| 값 | matcher | 비고 |
| --- | --- | --- |
| `mock` | `MockDriverMatcher` | dev / test — DRV-2026-001~005 (INTERNAL) 만 |
| `insung` | `InsungQuickDriverMatcher` | 인성데이타 5만 프리랜서 풀 (W10-2 통합) |

### 6-2. 매칭 score 기준 (W10-2 spec — 현재는 설계만)

> ⚠️ 현 W10-1 시점에는 score 가중치 미구현. `MockDriverMatcher` 는 항상 driverCode `MOCK-001` 단일 driver 반환 (DB 없으면 자동 생성), `InsungQuickDriverMatcher` 는 placeholder (`UnsupportedOperationException`). 아래 표는 **W10-2 인성데이타 vendor 통합 시점 활성 예정 spec** 입니다.

| 항목 | 가중치 (W10-2 spec) | 비고 |
| --- | --- | --- |
| 차량 톤수 ↔ driver vehicleType | 0.4 | 일치 시 만점 |
| 정차 위치 ↔ driver 거주지 | 0.3 | 인성데이타 5만 풀에서 거리 score |
| driver appInstalled (INTERNAL 우선) | 0.2 | INTERNAL 만점 |
| 최근 배차 history | 0.1 | (W10-2 후 활성) |

W10-1 mock 동작 (실 코드 — `services/arologis-service/src/main/java/com/samhanair/logis/arologis/matcher/MockDriverMatcher.java`):

| 항목 | 값 |
| --- | --- |
| driverCode | `MOCK-001` (상수 — 단일 mock driver 재사용) |
| phoneNumber | `010-0000-0000` |
| vehicleType | `1톤` |
| source | `INTERNAL` |
| externalRef | `MOCK-<random8>` (call 마다 신규) |

> dev seed (`DriverSeeder` — 10명 DRV-2026-001 ~ 010) 와 별개. mock matcher 의 `MOCK-001` 은 활성 matcher 가 mock 일 때만 자동 생성됩니다.

> P3 backlog — W10-2 score 가중치 실 구현 + 가시화 / 사용자 보정 UI.

## 8. FAQ + 트러블슈팅

| 증상 | 원인 | 해결 |
| --- | --- | --- |
| 파싱 결과 빈 vehicles | 헤더 라인 매칭 실패 | `8일착 야상입니다` 형식 정정 |
| 톤수가 모두 `1톤` | 톤수 라인 누락 | 차량 그룹 끝에 `1톤` / `2.5톤` 추가 |
| `2. -경기...` 가 차량 만 인식되고 정차 누락 | parser 버그 (W10-1 fix 됨) | 최신 버전 확인 |
| 정차에 `unparsed: true` 라인이 많음 | 형식 미준수 (괄호 / 사업자명) | 단톡방 발송자에게 표준 안내 |
| 자동 매칭 0건 | DriverMatcher 가 placeholder (UnsupportedOperationException) | matcher 활성 설정 확인 / 개발팀 |
| 매칭 후 driver 어플에 알림 미수신 | `NotificationClient` 비활성 / driver `appInstalled=false` | INTERNAL driver 만 push 가능 — INSUNG/KAKAO 는 외부 SMS / 카톡 |
| 동일 메시지 두 번 저장 → 중복 dispatch | idempotency 미적용 | 본 endpoint 는 idempotency-key 없음 — 운영자가 list 조회 후 중복 확인 (Phase 11 후 P3 보강) |
| `kakaoText 필수` 400 | body 가 비어있음 | request body `{"kakaoText": "..."}` 형식 확인 |
| `403 Forbidden` | ROLE 미부여 | MASTER / MANAGER 만 호출 가능 |
