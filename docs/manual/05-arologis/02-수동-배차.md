## 1. 현재 우회 방법 (P1-5 admin 폼 부재 시)

### 1-1. 우회 1 — 카카오톡 형식으로 직접 작성

전용 admin 폼이 부재하므로, 카카오톡 메시지 형식 ([01. 카카오톡 배차](01-카카오톡-배차.md) §1) 으로 직접 작성하여 `POST /admin/arologis/dispatches` 호출.

```
8일착 야상입니다
1. 본사창고
-서울 강남구 역삼동(현대공조-501)10시
1톤
```

→ `POST /admin/arologis/dispatches` body:
```json
{ "kakaoText": "8일착 야상입니다\n1. 본사창고\n-서울 강남구 역삼동(현대공조-501)10시\n1톤" }
```

→ 응답 `{ "dispatchId": "..." }`.

### 1-2. 우회 2 — backend 직접 INSERT (P0-5 사용자 UI 부재 패턴 동일)

개발팀에 SQL 요청. 권장 X — audit trail 누락 위험.

```sql
INSERT INTO dispatches (id, dispatch_date, dispatch_type, raw_kakao_text, ...)
VALUES (gen_random_uuid(), '2026-05-08', 'NIGHT', '(수동입력)', ...);
```

> ⚠️ Soft Delete / BaseEntity audit 7 필드 누락 → BE-2 가드 위반. 운영팀 우회만, 정식 입력은 §1-1 권장.

## 3. 정차 상태 갱신

### 3-1. StopStatus 7 단계

| 상태 | 의미 | 운영 | 트리거 |
| --- | --- | --- | --- |
| **UNPARSED** | 카톡 파싱 실패 (보정 대기) | admin | parser |
| **PENDING** | 배차 직후 (대기) | 자동 | DispatchService.create |
| **DISPATCHED** | driver 배정 완료 | 자동 | autoMatch / assignDriverManual |
| **EN_ROUTE** | 출발 (이동 중) | 모바일 / admin | driver-app GPS / admin |
| **ARRIVED** | 거래처 도착 | 모바일 / admin | driver-app / admin |
| **COMPLETED** | 서명 완료 (정상) | 자동 | driver-app sign |
| **FAILED** | 미배달 / 부재중 | admin | admin 보정 |

### 3-2. admin 정차 상태 변경

`PUT /admin/arologis/dispatches/{id}/vehicles/{seq}/stops/{stopSeq}/status` body `{ "status": "ARRIVED" }`.

화면 (P1-5 fix 시) → 정차 라인 우측 [상태 변경] → 드롭다운 → 저장.

![정차 상태 변경](../screenshots/05-arologis/02-stop-status-change.png)

> 모바일 driver-app 의 sign 호출이 자동으로 COMPLETED 갱신하므로, admin 보정은 예외 상황 (서명 누락 / 부재중 등) 만.

## 4. Dispatch Soft Delete

`PUT /admin/arologis/dispatches/{id}/delete` 호출. BaseEntity.markDeleted 적용 (audit 보존).

UI (P1-5) → list 화면에서 row 우측 [삭제] → 확인 dialog → soft delete.

> ⚠️ Soft Delete 후 list 응답에서 자동 제외. DB 에는 `deleted_at` / `deleted_by` 만 채워지고 row 보존. 복원은 개발팀 SQL.

## 5. 권한 + 운영자 시점 ROLE

| 작업 | MASTER | MANAGER | SALES | DRIVER |
| --- | :-: | :-: | :-: | :-: |
| Dispatch 저장 | ✅ | ✅ | ❌ | ❌ |
| 정차 상태 갱신 | ✅ | ✅ | ❌ | ❌ (자동만) |
| 수동 driver 배정 | ✅ | ✅ | ❌ | ❌ |
| Soft Delete | ✅ | ✅ | ❌ | ❌ |

> 별도 `DISPATCH` ROLE 은 backlog. 현재는 MANAGER 또는 MASTER 만 admin 호출 가능 (`@PreAuthorize("hasAnyRole('MASTER','MANAGER')")`).

## 6. 트러블슈팅 + FAQ

| 증상 | 원인 | 해결 |
| --- | --- | --- |
| `kakaoText 필수` 400 | body 미입력 | `{"kakaoText": "..."}` 형식 확인 |
| `헤더 라인 파싱 실패` 400 | `8일착 야상입니다` 누락 | 첫 줄 헤더 추가 후 재호출 |
| 톤수가 모두 `1톤` | 톤수 라인 누락 | 차량 그룹 끝에 `1톤` 등 추가 |
| Dispatch 저장 후 list 에 안 보임 | 날짜 필터 다름 | `GET /admin/arologis/dispatches?date=2026-05-08` 명시 호출 |
| 같은 Dispatch 두 번 저장됨 | idempotency 부재 | 운영자가 list 조회 후 중복 → soft delete |
| 정차 상태 갱신 시 404 | seq / stopSeq 불일치 | `GET /admin/arologis/dispatches/{id}` 로 정확한 sequence 확인 |
| `403 Forbidden` | SALES / DRIVER ROLE | MASTER / MANAGER 만 admin endpoint 호출 가능 |
| Soft Delete 후 복원 필요 | UI 부재 | 개발팀에 `UPDATE dispatches SET deleted_at=NULL WHERE id=...` SQL 요청 |

## 6-1. 수정 이력 보기 + DISPATCHED 잠금 + SMS 알림 (Phase 12 step-4c, PR-H4c FE rollout)

> **PR-H4c 변경** — Dispatch 의 모든 필드 (기사명/차량/예정시각/경로) 는 변경될 때마다 audit log 가 누적되며, DispatchDetailPage 화면에서 "취소선 + 수정자 색상 + 수정자 이름" overlay 로 한눈에 확인할 수 있습니다. 사용자 명시 패턴 (`docs/uiux/phase12/H2-audit-overlay.md`) arologis 도메인 적용 — slip 화면과 시각 1:1 동일.

### 6-1-1. 배차 헤더 "수정 N회" badge

DispatchDetailPage 우측 상단에 **수정 N회** badge 표시 (PR-H2 시드와 동일 임계 색상).

### 6-1-2. 필드별 audit overlay (기사명 / 차량 / 예정시각)

각 필드 우측에 가장 최근 변경:

```
기사명             김철수                ~~홍길동~~          ● 정배차 13:32 (기사 변경 — SMS 발송)
기사 연락처        010-9999-8888         ~~010-1234-5678~~   ● 정배차 13:32
차량번호           12가 3456 (1톤)       (시드 그대로)
예정시각           2026-05-10 15:00      (시드 그대로)
운송 경로          서울 본사 → 부산 창고 (시드 그대로)
```

### 6-1-3. PLANNED 자유 수정 → DISPATCHED 잠금

- `PLANNED` (작성 단계) — 자유 수정. DISPATCHER / MANAGER / MASTER 모두 가능
- `DISPATCHED` (기사 출발) — LOCKED_REQUIRES_APPROVAL — 수정 요청 워크플로우

```
[잠금 banner — DISPATCHED]
이 배차는 잠금 상태입니다 — 수정 요청을 보내주세요.
DISPATCHED 상태 = 활성 승인 1회 한정 mutation. 변경 시 권한자 (MANAGER) 승인 필요.

[+ 수정 요청]
```

### 6-1-4. IN_TRANSIT FULLY_LOCKED (운송 중 — 운송 사고 안전)

`IN_TRANSIT` (운송 중) 또는 `DELIVERED` (완료) 상태는 직접 수정 불가:

```
[잠금 banner]
이 배차는 완전 잠금 상태입니다 — MASTER 본부 승인 별도 절차 필요.
운송 중 변경 = 기사 혼선 + 운송 사고 직결. MASTER 본부 승인 별도 절차로만 가능.
```

### 6-1-5. 기사 변경 SMS 자동 발송 (post-approve hook)

기사 정보 (driverName / driverPhone) 변경 승인 후 mutation 시 자동 SMS 발송:

```
[우측 상단 toast — 기사 변경 후]
기사 변경 SMS 발송 완료 — 이전 기사 (홍길동) + 새 기사 (김철수) 양쪽 발송.
NotificationClient.sendSms ×2 (운송 사고 방지 의무)
```

> 본 동작은 PR-H4b BE rollout 의 `DispatchEditRequestService` post-approve hook 으로 자동 처리. SMS 발송 실패 시 별도 알림 toast (DISPATCHER 가 수동 연락 필요).

### 6-1-6. 1초 SSE 실시간 sync (multi-context — DISPATCHER / MANAGER / DRIVER)

DISPATCHER 가 배차를 수정하면 동시에 화면을 보고 있던 MANAGER / DRIVER (모바일) 의 화면이 1초 안에 자동 갱신.

```
[우측 상단 toast]
실시간 변경 감지 — 0.8초
정배차 님이 기사명 을 "김철수" 으로 수정했습니다. (rev #1 — SMS 발송 완료)
```

### 6-1-7. UUID 비공개 + dispatchNo 노출

화면 어디에도 UUID 노출 0건. 비즈니스 식별자만 표시:

- 배차번호 (`D-2026-0510-007`) / 차량번호 (`12가 3456`) / 기사명 (`김철수`)
- actorName 풀네임 + 색상 dot

### 6-1-8. mobile-staff DispatchDetailScreen RN 1:1

기사 (DRIVER) 가 모바일에서 자기 배차를 조회하는 경우 RN audit overlay 가 desktop 과 동일 시각 (취소선 + 색상 dot + 한국어 라벨) 으로 렌더링 — `userIdToColor` deterministic hash 동일.
