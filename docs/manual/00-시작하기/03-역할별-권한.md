## 1. 9개 ROLE 정의

ROLE 은 사용자 등록 시 1개만 부여되며 (1 user = 1 role), 여러 부서 겸직은 시스템 외부 정책으로 처리. 본 매뉴얼은 **풀네임으로만 표기** (메모리 가드).

| 풀네임 | 한글 | 책임 | 시드 인원 |
| --- | --- | --- | :-: |
| **MASTER** | 대표 / 시스템 관리자 | 회사 대표(김미선) + 슈퍼 권한 (전 service 전 endpoint) | 1 |
| **MANAGER** | 부서장 | 영업총괄 / 창고소장 / 회계과장 — 부서별 결재 / 거절 권한 | 1+ |
| **SALES** | 영업직원 | 거래처 등록 / 슬립 발행 / 견적 / 주문 | 다수 |
| **WAREHOUSE** | 창고작업자 | 출고 패킹 / 입고 검수 (작업 단계) | 다수 |
| **INVENTORY** | 재고관리자 | 재고 이동(transfer) / 재고 조정(adjust) | 1~2 |
| **ACCOUNTANT** | 회계담당 | 분개 입력 / 슬립 정산(CONFIRMED) / 보고서 | 5 (시드) |
| **PARTNER** | 외부 거래처 | 주문서 작성 / 본인 주문 history 조회 | (외부) |
| **DRIVER** | 배송기사 | 모바일 서명 (slip DELIVERED) | 다수 |
| **DEVELOPER** | 개발팀 | read-only 전체 + 일부 master data | 1~2 |

### 1-1. 시스템 내부 가상 ROLE (사용자 부여 불가)

| 풀네임 | 사용처 |
| --- | --- |
| **INTEGRATION** | 서비스 간 호출 (X-Internal-Token) — slip-service ↔ accounting-service 등 |
| **PARTNER_ADMIN** | 거래처측 결재자 (PARTNER 의 상위) — partner-order-service 일부 endpoint |

## 4-2. 슬립 수정/삭제 잠금 정책 (Phase 12 step-3, PR-H3)

> **PR-H3 변경** — 슬립 status 별로 4단계 잠금이 적용되며, 잠금 단계마다 수정 요청/수락 권한자가 다릅니다. 자세한 워크플로우는 [02-창고/02. 출고 처리 §2-10](../02-창고/02-출고-처리.md#2-10-수정--삭제-요청-워크플로우-phase-12-step-3-pr-h3) 참조.

### 4-2-1. 잠금 단계 4분류

| 잠금 단계 | 적용 status | 수정 가능 ROLE (직접) | 요청 수락 권한 ROLE | unlock 시간 |
| --- | --- | --- | --- | --- |
| **0차 (잠금 없음)** | `DRAFT` / `SAVED` | 본인 SALES + MANAGER + MASTER | (요청 절차 없음) | (잠금 없음) |
| **1차 잠금** | `SENT` / `ACCEPTED` / `PROCESSING` / `REJECTED` | MANAGER + MASTER | MANAGER + MASTER | 24시간 |
| **2차 잠금 (사유 200자 필수)** | `INSPECTING` / `COMPLETED` / `SHIPPING` / `DELIVERED` | MASTER | **MASTER** (MANAGER 는 검토 의견만 첨부 가능) | 1시간 |
| **영구 잠금** | `CONFIRMED` / `CANCELED` | (회계 역분개 절차로만) | — | (수정 불가) |

| 슬립 상태 | 영문 | 본인 SALES | SALES 다른 직원 | MANAGER | MASTER | ACCOUNTANT |
| --- | --- | --- | :-: | --- | --- | :-: |
| 작성중 | `DRAFT` | 자유 수정/삭제 | ❌ | 자유 수정/삭제 | 자유 수정/삭제 | ❌ |

| 수락 | `ACCEPTED` | 요청 후 수락 시 (24h) | ❌ | 직접 수정 + 요청 수락 | 직접 수정 | ❌ |
| 처리중 | `PROCESSING` | 요청 후 수락 시 (24h) | ❌ | 직접 수정 + 요청 수락 | 직접 수정 | ❌ |

| 출하중 | `SHIPPING` | 요청 (사유 200자) | ❌ | 검토 의견 첨부 | 직접 수정 + 요청 수락 (1h) | ❌ |

| 반려 | `REJECTED` | 요청 후 수락 시 (24h, 재기안) | ❌ | 직접 수정 + 요청 수락 | 직접 수정 | ❌ |

### 4-2-3. 1차 vs 2차 잠금 차이

| 항목 | 1차 잠금 | 2차 잠금 |
| --- | --- | --- |
| 사유 글자 수 | 50자 권장 | **200자 이상 강제** |
| 비즈니스 카테고리 | 없음 | **거래처 요청 / 재고 차질 / 법적 사유 / 기타** 4 옵션 중 1개 필수 |
| 수락 권한 ROLE | MANAGER (즉시 수락) | **MASTER** 만 |
| MANAGER 의 역할 (2차) | — | 검토 의견만 첨부 (수락/거절 권한 없음) |
| unlock 시간 | 24시간 | **1시간** |
| audit log | 누적 | **영구 보존 + 감사 표시** |
| banner 색상 | 노랑 | 빨강 (위험 강조) |

### 4-2-4. 삭제 권한

| status | 본인 SALES | MANAGER | MASTER | 비고 |
| --- | :-: | :-: | :-: | --- |
| `DRAFT` / `SAVED` | ✅ 즉시 삭제 | ✅ 즉시 삭제 | ✅ 즉시 삭제 | 요청 절차 없음 |
| `SENT` ~ `DELIVERED` | 요청 후 수락 시 | 직접 삭제 + 요청 수락 | 직접 삭제 + 요청 수락 | 1차 잠금과 동일 절차 |
| `CONFIRMED` | ❌ | ❌ | 회계 역분개 후 가능 | 회계 영역 |
| `CANCELED` | ❌ (영구) | ❌ (영구) | ❌ (영구) | 신규 발행으로 대체 |

> **삭제 = soft delete + CANCELED** — `deleted_at` 컬럼 set + 화면 hide. audit log 영구 보존. 회계 분개가 있다면 자동 역분개 큐 (accounting-service 연동, 후속 PR).

### 4-2-5. WAREHOUSE / INVENTORY / DRIVER / PARTNER 의 권한

본 잠금 정책은 영업이 작성한 슬립 본문의 수정/삭제에 한정됩니다. 출고 처리 절차 (accept/process/inspect/complete/ship/deliver) 는 §4 기존 매트릭스 그대로 — WAREHOUSE / INVENTORY 가 진행합니다.

| ROLE | 본 잠금 정책 영향 | 비고 |
| --- | --- | --- |
| WAREHOUSE | ❌ 수정/삭제 권한 없음 | 출고 절차만 진행 |
| INVENTORY | ❌ 수정/삭제 권한 없음 | 출고 절차만 진행 |
| DRIVER | ❌ 수정/삭제 권한 없음 | 모바일 서명만 |
| PARTNER | ❌ 수정/삭제 권한 없음 | 거래처 주문 자체 수정만 (별도 정책) |
| ACCOUNTANT | ❌ 슬립 본문 수정 불가 | CONFIRMED 후 회계 분개 영역만 |
| DEVELOPER | △ read-only | 운영 데이터 디버깅용 |

## 7. 본인 ROLE 확인 + 변경 요청

### 7-1. 본인 ROLE 확인

화면 우상단 본인 이름 → 드롭다운 → **[내 프로필]** (P1-2 — UI 미구현).

임시 우회 — 사이드바 메뉴 구성으로 확인 (위 §2 표 대조) 또는 IT 관리자에게 문의.

### 7-2. ROLE 변경 요청

ROLE 변경은 **MASTER 만** 가능 — `PATCH /users/employees/{id}/role`.

#### 절차

1. 본인 → 직속 부서장(MANAGER) 에게 변경 사유 공식 요청
2. 부서장 → MASTER (또는 인사 담당) 에게 escalation
3. MASTER 가 desktop UI (P0-5 미구현 — 현재 backend API 직접 호출 또는 DB 변경) 로 변경
4. 변경 후 본인 재로그인 → JWT 갱신 → 새 ROLE 적용

> ⚠️ **현재 P0-5 미구현** — desktop 의 직원 / 권한 관리 UI 가 부재합니다. ROLE 변경은 IT 관리자 또는 개발팀이 backend API 로 직접 수행 (예상 fix: Phase 11 진입 전 1 PR).

## 8. 자주 묻는 질문 (FAQ)

**Q1. 한 사용자가 SALES + ACCOUNTANT 겸직 가능한가요?**
A. 시스템상 1 user = 1 role 입니다. 겸직은 두 계정을 발급받아 분리 사용. 또는 MANAGER 권한으로 통합 (MANAGER 는 영업/회계 모두 결재 가능).

**Q2. PARTNER ROLE 도 desktop 에 접속 가능한가요?**
A. 불가. 거래처 전용 PWA (`https://order.samhan-air.com`) 만 접근. partner-auth-service 별도 인증.

**Q3. DRIVER 가 슬립 list 를 볼 수 있나요?**
A. 불가. 본인이 배정된 DeliveryBatch (share token URL) 만 모바일에서 조회 가능. desktop 미접근.

**Q4. DEVELOPER ROLE 은 무엇인가요?**
A. 개발팀 read-only — 운영 데이터 디버깅용. 일부 master data (제품/창고) 만 write 가능. 운영 작업 (슬립 발행 등) 은 불가.

**Q5. ROLE 이 변경되었는데 메뉴가 그대로입니다.**
A. JWT 캐시. 로그아웃 → 재로그인 후 갱신.

**Q6. INTEGRATION / PARTNER_ADMIN 은 어떤 사용자에게 부여되나요?**
A. 시스템 가상 ROLE — 사용자 부여 불가. service 간 호출 시 자동 임시 부여 (X-Internal-Token).

**Q7. 새 ROLE 을 추가하고 싶습니다.**
A. ROLE enum 은 코드 변경 필요 (개발팀). 운영 중 추가 불가 — `backend-feature-inventory.md` §3.4 "❌ 권한 그룹 / 역할 (Role) CRUD" 참조 (장기 backlog).

## 9. 트러블슈팅

| 증상 | 원인 | 해결 |
| --- | --- | --- |
| 메뉴가 표시되어야 하는데 안 보임 | ROLE 미부여 / JWT 만료 | 재로그인 → 그래도 없으면 IT 관리자에게 ROLE 확인 요청 |
| 버튼은 보이는데 클릭 시 403 | endpoint 단위 권한 부족 | 위 §3 service 표 대조 + MANAGER 에게 권한 위임 요청 |
| ROLE 변경 후 이전 메뉴가 남아있음 | 브라우저 캐시 | Ctrl+Shift+Delete (캐시 삭제) → 재로그인 |
| MASTER 인데 일부 endpoint 가 안 됨 | endpoint 가 INTEGRATION 전용 | 정상 — MASTER 라도 service 간 호출 endpoint 는 직접 호출 불가 (X-Internal-Token 필요) |
| PARTNER 가 desktop 접속 시 빈 화면 | 정상 — PARTNER 는 desktop 미접근 | 거래처 PWA 안내 |
| DRIVER 가 SMS 링크 클릭 시 403 | shareToken 만료 | 영업/창고에 [shareToken 재발행] 요청 |

## 9-1. 수정 이력 / 잠금 정책 종합 (Phase 12 step-4c, PR-H4c FE rollout — 9 도메인 일람)

> **PR-H4c 변경** — Phase 12 step-2~4 슬라이스로 9 도메인 50+ page 가 audit overlay + edit-request 잠금 정책을 일관 도입했습니다. 본 절은 9 도메인 잠금 정책 종합 일람표로, 사용자가 어떤 화면에서 어떤 잠금 banner 를 만나게 되는지 미리 학습 가능하도록 설계.

### 9-1-1. 잠금 분류 3종 (전 도메인 일관)

| 분류 | UI 분기 | 시각 표시 | 의미 |
| --- | --- | --- | --- |
| **FREE_DIRECT_EDIT** | 모든 input 활성 | (banner 없음) | 자유 수정 단계 — 작성자 + 권한자 즉시 수정 가능 |
| **LOCKED_REQUIRES_APPROVAL** | input 비활성 + banner | 노랑 banner + `[+ 수정 요청]` 버튼 | 수정 요청 → 권한자 승인 → 1회 한정 mutation |
| **FULLY_LOCKED** | input 비활성 + banner | 빨강 banner | MASTER 만 별도 절차로 수정 가능 (도메인별 별도 절차 — 정정 분개 / 운송 본부 승인 등) |

### 9-1-2. 9 도메인 × status × 잠금 분류 종합 일람

| 도메인 | DRAFT/PLANNED 등 free | 중간 잠금 (locked-approval) | 완전 잠금 (fully-locked) | 별도 정정 절차 |
| --- | --- | --- | --- | --- |
| **slip (전표)** | DRAFT / SAVED | SENT / ACCEPTED / PROCESSING / REJECTED | INSPECTING / SHIPPING / DELIVERED / CONFIRMED / CANCELED | PR-H3 §2-10 |
| **partner (거래처)** | DRAFT | ACTIVE | SUSPENDED / INACTIVE | MASTER 별도 절차 |
| **inventory (재고조정)** | DRAFT | SUBMITTED | POSTED / VOIDED | 회계 정정 분개 |
| **accounting (분개)** | DRAFT | (없음 — 직접 FULLY_LOCKED) | POSTED / CLOSED / VOIDED | 정정 분개 / 감사인 동석 |
| **arologis (배차)** | PLANNED | DISPATCHED | IN_TRANSIT / DELIVERED / CANCELED | 운송 본부 승인 |
| **product (품목)** | DRAFT | ACTIVE | DISCONTINUED / INACTIVE | MASTER 별도 |
| **dc-config (할인규칙)** | DRAFT | ACTIVE | EXPIRED / INACTIVE | MASTER 별도 |
| **partner-order (거래처주문)** | DRAFT | SUBMITTED | CONFIRMED / FULFILLED / CANCELED | MASTER 별도 |
| **user (사용자)** | (본인) ACTIVE | (없음 — audit only) | SUSPENDED / INACTIVE | MASTER 별도 |
| **groupware (메모/공지)** | DRAFT / PUBLISHED | (없음 — audit only) | ARCHIVED | MASTER 별도 |
