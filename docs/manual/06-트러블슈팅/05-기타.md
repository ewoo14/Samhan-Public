## 1. DB 연결 오류 (PostgreSQL 다운)

### 1-1. 증상

- 모든 화면에서 빨강 토스트 "데이터를 불러올 수 없습니다"
- backend log `Connection refused: localhost:5432`
- F12 Network — 모든 요청이 500 또는 timeout

### 1-2. 진단 (IT 관리자)

```bash
# PostgreSQL container 상태
docker ps | grep postgres

# 또는 직접 ping
psql -h localhost -p 5432 -U postgres -d samhan_auth -c "SELECT 1;"
```

응답 없음 / Connection refused = PostgreSQL 다운.

### 1-3. 해결

1. **IT 관리자**: PostgreSQL container 재시작
   ```bash
   docker-compose restart postgres-auth postgres-user postgres-slip ...
   ```
2. 30초 대기 → 각 service 가 자동 재연결
3. Phase 11 후 AWS RDS — Multi-AZ + Auto Recovery (`project_phase11_aws.md`)
4. 미해결 → 개발팀 escalation

### 1-4. service-per-DB 구조

본 시스템은 **service 별 1 DB** (CQRS). 한 DB 만 다운 시 일부 service 만 영향:

| 다운 DB | 영향 service | 영향 범위 |
| --- | --- | --- |
| samhan_auth | auth-service | 모든 로그인 차단 |
| samhan_user | user-service | 직원 / ROLE 조회 |
| samhan_partner | partner-service | 거래처 |
| samhan_slip | slip-service | 슬립 / 배송 |
| samhan_inventory | inventory-service | 재고 |
| samhan_accounting | accounting-service | 분개 / 시산표 |
| samhan_arologis | arologis-service | 배차 (Phase 10) |
| samhan_dashboard | dashboard-service | 대시보드 |

## 2. 시드 (Seed) 데이터 미적용

### 2-1. 증상

- 처음 로그인 시도 시 모든 계정 401 (사용자 없음)
- 거래처 list 비어있음
- arologis driver / dispatch 비어있음 (dev 환경)

### 2-2. 원인

| 원인 | 영향 |
| --- | --- |
| `app.bootstrap.seed` 또는 `app.arologis.seed-test-data` profile 누락 | 시드 미실행 |
| Spring Profile = `dev` 미설정 | DriverSeeder / DispatchSeeder 비활성 (`@Profile("dev")` 가드) |
| DB volume 신규 생성 (docker volume rm) | 모든 데이터 초기화 |
| seed runner 실패 (Order 충돌 / FK 위배) | 일부만 시드 |
| Production 환경 (`app.bootstrap.seed=false`) | 정상 — production 은 시드 사용 X |

### 2-3. 해결

#### dev 환경

```bash
SPRING_PROFILES_ACTIVE=dev \
APP_AROLOGIS_SEED_TEST_DATA=true \
APP_BOOTSTRAP_SEED=true \
docker-compose up
```

#### production 환경 (Phase 11)

1. **MASTER 계정 1개 사전 등록** — `POST /auth/register` (운영 시작 시 1회)
2. 이후 직원 등록 = MASTER 가 desktop UI (P0-5 fix 후) 또는 backend API
3. 거래처 등록 = SALES / MANAGER 가 desktop UI (P0-6 fix 후)

### 2-4. 시드 표

| Seeder | 위치 | 활성 조건 | 데이터 |
| --- | --- | --- | --- |
| OrgChartSeeder | user-service | dev | 부서 5개 + 직원 16명 |
| DriverSeeder | arologis-service | dev + `app.arologis.seed-test-data=true` | driver 10명 |
| DispatchSeeder | arologis-service | dev + `app.arologis.seed-test-data=true` | dispatch 20건 |
| AccountSeeder | accounting-service | dev | 표준 계정과목 100/200/300/400/500/800/900 |
| ProductSeeder | product-service | dev | 제품 카탈로그 |

## 4. 자주 발생하는 backend 오류

### 4-1. `Eureka 비활성` (service discovery 실패)

```
RestClientException: I/O error on POST request for "http://slip-service/...":
  Connection refused
```

원인 — Eureka 가 service 를 발견하지 못함 (등록 지연 또는 service 다운).

해결:
1. Eureka 화면 확인 — `http://eureka.samhan-air.com:8761`
2. 등록되지 않은 service 재시작
3. 30초~2분 대기 (registry sync)

### 4-2. `IT 외부 RestClient 미설정` (테스트 환경)

`feedback_it_mockbean_external_clients.md` 가드 — IT 환경의 `@SpringBootTest` 테스트 가 외부 client (`ProductClient` / `InventoryClient` / `SlipClient`) 를 `@MockBean` 으로 격리하지 않으면 Eureka 비활성 → 500.

운영자 영향 X (개발자 환경 만). 운영 시 발생 시 = 개발팀 즉시 보고.

### 4-3. `403 Forbidden — INTERNAL token 누락`

```
{
  "code": "FORBIDDEN",
  "message": "X-Internal-Token 필요"
}
```

원인 — service 간 호출 endpoint (`/internal/...`) 를 일반 사용자가 직접 호출.

해결 — endpoint 가 INTEGRATION ROLE 전용. 정상 운영자는 호출 불가. 호출 필요 시 개발팀 승인 → admin endpoint (`/admin/...`) 로 우회 가능 여부 확인.

## 5. UUID 노출 회피 (메모리 가드)

### 5-1. 증상

- 화면 / 로그 / 인쇄에 UUID (예: `7a3f-b9c2-...`) 노출

### 5-2. 가드

`feedback_uuid_no_user_visibility.md` — 모든 클라이언트 화면에서 UUID 노출 금지. 비즈니스 식별자만 노출:

| 도메인 | UUID (내부) | 사용자 노출 식별자 |
| --- | --- | --- |
| 슬립 | `slip.id` | `slipNumber` (S-2026-NNNNN) |
| 거래처 | `partner.id` | `partnerCode` (P-2026-NNNN) |
| 직원 | `employee.id` | `employeeNumber` (EMP-2026-NNN) |
| 제품 | `product.id` | `productCode` (PRD-NNN) / `modelName` |
| 창고 | `warehouse.id` | `warehouseCode` (HQ-001 / VH-001) |
| 기사 | `driver.id` | `driverCode` (DRV-2026-NNN) |
| Dispatch | `dispatch.id` | `dispatchNumber` (P3 backlog — 현재 dispatchId 노출 — admin 만) |

### 5-3. 노출 발견 시

운영자가 화면에서 UUID 발견 → 개발팀에 즉시 보고 + 화면 캡처 + 시간 기록 (가드 위반 회고 — 본 PR 회고 패턴).

## 7. 데이터 백업 / 복원 (P0-8 Phase 11 후 정식)

### 7-1. 현재 상태 (운영 시작 전)

⚠️ **백업 정책 미정** (P0-8). Phase 11 진입 전 1 PR 권고.

- RDS 자동 백업 (default 7일) — 권장 30일
- 일별 snapshot — Phase 11 cutover 시 활성
- 분기별 cold storage (S3 Glacier) — 장기 보관

### 7-2. 운영자 시점 (백업 활용 안내 — Phase 11 후)

- 데이터 손실 의심 시 → IT 관리자에게 RDS snapshot 복원 요청
- snapshot 복원 = read-only DB 복제 → 데이터 export 후 정식 DB 에 INSERT
- 복원 시간 = 보통 30분~2시간 (DB 크기에 따라)

## 8. FAQ

**Q1. 데이터를 잘못 입력했습니다. 복원 가능한가요?**
A. Soft Delete 방식 — 삭제 후에도 DB 에 row 보존. 개발팀 SQL 로 복원 가능 (`UPDATE ... SET deleted_at=NULL`). 단순 데이터 변경 = 새 row update 만, 이전 값은 audit log (logging-service) 조회.

**Q2. 동일 슬립이 두 번 발행되었습니다.**
A. idempotency-key 가 있는 endpoint 는 중복 차단. 슬립은 발행 시점에 idempotency 미적용 — 운영자 수동 cancel 필요. 거래처 주문 → 슬립 자동 변환은 idempotent (`POST /partner-orders/{id}/confirm`).

**Q3. service 일부만 다운되었는데 작업 계속 가능?**
A. 영향받은 service 의 메뉴 외에는 사용 가능. 예: arologis-service 다운 = 배차 메뉴만 차단, 영업 / 창고 / 회계는 정상.

**Q4. 백업 데이터를 직접 다운로드 할 수 있나요?**
A. 운영자는 불가 — 보안 정책. IT 관리자가 RDS snapshot → S3 export → 운영자에게 안전한 채널로 전달 (요청 시).

**Q5. 시스템이 너무 느립니다.**
A. 1) 본인 PC 성능 (기준 RAM 8GB+) 2) 데이터량 (슬립 list 의 from-to 좁히기) 3) 시간대 (점심 / 마감 시 부하 집중) 4) IT 관리자에게 보고 → DB Performance Insights 확인.

**Q6. 한국 시간대 (KST) 가 정확한가요?**
A. 모든 service `TZ=Asia/Seoul`. 화면 표시 = KST. DB 저장 = UTC + zone 변환 (BaseEntity.createdAt). 시간 차이 발견 시 개발팀 보고.

**Q7. 외부 vendor (Aligo SMS / 인성데이타 / Hometax e-Tax) 통합 시 추가 비용?**
A. 별도 vendor 계약 — IT / 회계 부서 협의. Phase 11 후 단계적 통합.
