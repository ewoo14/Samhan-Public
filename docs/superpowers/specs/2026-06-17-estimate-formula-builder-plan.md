# 기획 — 종합견적서 계산 수식/규칙 메뉴 설정화 (수식 빌더)

> 2026-06-17 개발책임자 요청: "추후 신규 품목들이 지속 유입 → **메뉴에서 직접 견적서와 같은 수식을 구현**할 수 있는 방안 기획."
> 선행: 변동DC 토글(슬3-1, [[2026-06-17-formula-read-parity-slice3-1]]) + 종합견적서 설정 파라미터 18종 정찰.

## 1. 배경 / 문제

현재 종합견적서(estimate-app) 가격 계산은 **3중 의존**:
- **시트 수식**: `납품가 = 출고가 × (1 − IF(L열 개별DC, L열, $L$2 공통변동율)) − 옵션DC`, 배분/조합비 등 (`tools/legacy-gas`, `code.js`).
- **dc-config(거래처별 11파라미터)**: 운영 중(홈/상업 변동율, 옵션DC 6, 반올림 2, 유연호스).
- **하드코드 5 + 미구현 2**: 변동DC 기본율(0.45), VAT(10%), 배분비율(6:4), 조합비 경고, 천원정렬 / 카드수수료·선금할인(미구현).

**핵심 한계**: 신규 품목/카테고리/할인규칙이 들어오면 **시트 수식 또는 코드 수정**이 필요 → 비개발자(영업/관리)가 추가 불가, 시트-DB 이중 관리.

## 2. 목표

**메뉴(견적품목 관리 / 회계설정)에서 가격 계산 규칙을 정의**하여, 신규 품목도 코드/시트 수정 없이 견적 계산에 편입.

## 3. 방안 옵션 (난이도·유연성 trade-off)

### 옵션 A — 파라미터 설정 (값만 설정)
- 18 파라미터를 UI에서 설정(변동DC 공통율·카드수수료·조합비 경고·안내문구 등). **수식 구조는 코드 고정**.
- 신규 품목 = 기존 수식 유형(멀티/싱글/구형)에 분류 + 파라미터 적용.
- ✅ 단순·안전·즉시 가치. ❌ 새 **계산 패턴**(신규 할인 로직)은 여전히 코드.
- **변동DC 토글(슬3-1) = 이 옵션의 첫 조각.**

### 옵션 B — 계산 규칙 템플릿 (구조화된 규칙)
- 품목 유형(멀티/싱글세트/구형/신규)별 **계산 규칙을 템플릿화**: `base×(1−변동율)−옵션DC`, 배분(실내:실외), 조합비 검증 등. 각 단계가 파라미터화된 빌딩블록.
- UI: 품목/카테고리에 **템플릿 선택 + 파라미터 입력**. 신규 품목 = 템플릿 선택(코드 무).
- ✅ 유연 + 안전(템플릿 제약). 신규 품목 대부분 커버. ❌ 새 계산 *패턴*은 템플릿 추가(코드, 단 빈도 낮음).
- 데이터: `product_calc_template`(템플릿 정의) + 품목/카테고리↔템플릿 매핑.

### 옵션 C — 노코드 수식 빌더 (사용자 수식 정의)
- 사용자가 수식 직접 정의: **필드 참조**(출고가/수량/카테고리/사양) + **연산**(×÷+−) + **조건**(IF) + **함수**(반올림/올림/내림). 시트 `=LET(...)` 와 동등 표현력.
- 평가 엔진: **안전 샌드박스 파서**(임의 코드 실행 차단, 화이트리스트 함수/필드만). 서버측 평가 권위 + 감사로그.
- UI: 수식 에디터(블록형 권장 — 드롭다운 조합, 또는 제한 텍스트 + 검증).
- ✅ 최대 유연(신규 패턴도 코드 무). ❌ 복잡(파서·안전성·검증·디버깅·버전), 오류·오설정 위험, UX 난이도 높음.
- 데이터: `calc_formula`(수식 AST/표현식 + 적용 범위 + 버전).

## 4. 권장 — 단계적 (A → B → C)

| Phase | 옵션 | 내용 | 우선 | 위험 |
|---|---|---|---|---|
| **1** | A | 18 파라미터 설정 화면(변동DC 공통율·카드수수료·선금할인·조합비 경고·안내문구). `estimate_configs`(공통) + `dc_configs` 확장(결제). | P2(카드수수료 손실)~P3 | 낮음 |
| **2** | B | 품목 유형별 계산 규칙 템플릿 + 품목↔템플릿 매핑. 신규 품목 = 템플릿 선택. | P2 | 중 |
| **3** | C | 노코드 수식 빌더(B로 못 푸는 특수 케이스). 안전 샌드박스 + 서버 평가. | P3 | 높음 |

- **이유**: A는 즉시·저위험으로 "설정 가능" 비전 80% 충족. B가 "신규 품목 코드 무 편입"의 핵심. C는 진짜 임의 수식이 필요할 때만(과投資 경계). 시트 수식 표현력 대부분은 B 템플릿(변동율+옵션+배분+조합비)으로 커버됨이 정찰에서 확인.

## 5. 데이터 모델 (초안)

```
estimate_configs            -- 공통 단일행 (Phase 1)
  common_variable_dc_rate, vat_rate, combo_warn_home, combo_warn_comm, footer_text ...
dc_configs (확장)           -- 거래처별 (Phase 1)
  + card_fee_rate, advance_payment_discount_rate
product_calc_template       -- 계산 규칙 템플릿 (Phase 2)
  id, name, kind(MULTI/SINGLE/...), steps(jsonb: [{op, params}]), ...
product ↔ template 매핑      -- 품목/카테고리별 템플릿 (Phase 2)
calc_formula                -- 사용자 수식 (Phase 3)
  id, scope(품목/카테고리), expression(AST jsonb), version, ...
```

## 6. 계산 권위 / 안전

- **서버측 평가 권위**(estimate-app FE 미리보기 + dc-config-service/product-service 최종 계산). 기존 `PriceCalculationService` 확장.
- 감사로그(기존 `PriceCalculationLog` 패턴) — 어떤 규칙/수식으로 계산됐는지.
- C 도입 시 샌드박스(화이트리스트, 무한루프/임의코드 차단), 수식 검증·테스트 모드 필수.

## 7. 비-목표 / 경계

- 시트(legacy)는 Phase 진행에 따라 단계적 폐기(estimate-app DB-mode 전환과 연동, [[project_sheets_to_db_full_migration]]).
- VAT(법정 10%)·세트 배분(비즈니스 코어)은 설정화 우선순위 낮음(현행 유지).
- 본 기획은 **방향 제시** — 개발책임자 우선순위 확정 후 Phase별 spec 상세화.
