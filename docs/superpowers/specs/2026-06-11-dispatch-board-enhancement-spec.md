# SPEC — 배차 보드 고도화 에픽 (가배차 그룹핑·아로로지스 전송·실시간 협업·수정이력)

> 2026-06-11 개발책임자 지시(다회 메시지 종합). #463 완료배차 내역 뷰 실QA 중 **배차 보드 전체가 mock 전용(실 백엔드 미연동)** 임을 발견 → 실연동 + 본 고도화 요구사항을 함께 설계.

## 0. 선결 — 배차 보드 실연동 (mock → 실 백엔드)
배차 보드(`/dispatch-board`, `/arologis/*`)가 "TM 통합 시 검증" 보류로 **실 게이트웨이 미연동**이었음. 본 에픽의 모든 기능은 이 실연동이 전제.
- **게이트웨이 라우팅** — `/admin/dispatch-*` no-strip 라우트 추가 ✅(완료, board+#463 endpoint 200 확인).
- **응답 envelope** — dispatch 컨트롤러가 raw 반환(타 slip 컨트롤러는 ApiResponse 래핑) → FE `res.data.data` undefined → 빈 화면. **BE dispatch 컨트롤러 envelope 래핑 필요**(FE 이미 정상). ⏳

## 1. 차량 모델 — 2축(차종 + 톤수) 동적 종속 (개발책임자 확정)
현재 단일 enum(`DispatchVehicleType`: 오토바이·다마스·1톤~20톤, 종류+톤수 혼합)을 **2축 분리**:
- **차종(12)**: 오토바이 · 승용차 · 다마스 · 라보 · 카고 · 윙바디 · 탑차 · 리프트 · 냉장냉동탑 · 무진동 · 축차 · 추레라
- **톤수(10)**: 1톤 · 1.2톤 · 1.4톤 · 2.5톤 · 3.5톤 · 5톤 · 11톤 · 14톤 · 18톤 · 25톤
- **동적 종속**: 차종 선택 → 그에 맞는 톤수만 드롭박스에 노출(차종별 유효 톤수 매핑 필요 — 개발책임자 검토 후 확정).
- **기본값**: 차종=카고, 톤수=1톤.
- BE: `DispatchVehicleGroup` 의 vehicleType(단일 enum)을 `vehicleBodyType`(차종 enum) + `tonnage`(톤수 enum/값) 2필드로 확장. 마이그레이션 + DTO + arologis 전송 페이로드 동반. 기존 9 enum→신규 매핑(데이터 이행).

## 2. 그룹핑 + 아로로지스 전송 (미배차/가배차 리스트)
- **미배차 리스트 + 가배차 리스트 양쪽** 에 각각 [완료] 버튼 — 배차담당자가 각 리스트에서 아로로지스로 전송 가능.
- **체크박스 선택 전송(베스트)**: 차량(배차 그룹)별 체크박스 → 선택된 그룹들을 아로로지스로 전송. **차량별 개별 전송 + 전체 일괄 전송 모두** 지원.
- 전송 = 그룹핑된 전표 정보를 그룹 상태 그대로 아로로지스로 전송(현 `POST /admin/dispatch-tasks/{id}/dispatch` 골격 확장).

## 3. 전송 후 수정 + 수정이력/카운트/로그/회귀 (입출고전표 동형)
- 전송완료(DISPATCHED) 상태여도 **배차담당자가 다시 수정 가능**.
- 아로로지스 전송 상태에서 수정 시: **수정 카운트 + 수정내역(수정한 사람)** 표시 — 입출고전표와 동일 UX.
- **모든 수정 로그 저장 + 회귀(revert) 가능** — 입출고전표 revision/audit 패턴 재사용.
- (기존 Phase C MODIFICATION_* 상태 흐름 존재 — 이를 audit/카운트/회귀 UI 로 노출·확장.)

## 4. 영업 취소 → 취소선 + 아로로지스 연동
- 영업담당자가 전표 취소 → 해당 배차에 **즉시 취소선** + 취소 정보가 **아로로지스로도 전송**.
- (CANCEL_* 상태 흐름 + slip 취소 이벤트 ↔ dispatch 연동.)

## 5. 실시간 협업 표시 (Google Sheets 류) — 삼한 퍼블릭 ↔ 아로로지스 전반
- 위 모든 과정(전송·수정·취소)이 **실시간 화면 표시** — 같은 페이지를 보는 다른 사용자에게 수정 과정이 실시간 반영(Google Spreadsheet 류).
- **삼한 퍼블릭 + 아로로지스 양쪽 모두 동일**(실시간 화면 + 수정과정 표시).
- 기존 SSE 인프라(`product:catalog:changed` 등 afterCommit publish + FE 구독) 패턴을 dispatch 도메인에 적용(양 시스템 간 동기화 포함).
- **수정 = Google Docs 협업 모델**(개발책임자 추가 지시 2026-06-11): 실시간 협업 + **코멘트** + **수정제안(suggestion) 모드** — 수정하면 **기본적으로 "수정제안"처럼 적용**(즉시 확정 아님, 제안 → 수락/거절 흐름). 배차담당자·아로로지스 간 제안·코멘트·수락 협업. E3(수정이력/카운트/회귀)와 결합 — 제안 단위로 audit·revert. 구글 문서의 (a)실시간 동시편집 (b)코멘트 (c)제안 모드 3요소를 dispatch 수정 UX 의 레퍼런스로 삼는다.

## 6. 전표 문서 모달
- 그룹/리스트에서 **전표 선택 → 전표문서 모달** 표시(기존 `dispatch-board/components/SlipDetailModal.tsx` 존재 — 슬립 클릭에 배선/확장).

## 7. ★ 협업 편집 모델 = 시스템 전역 (개발책임자 2026-06-11 확장 지시)
**배차 한정이 아니다.** §3·§5의 Google Docs 협업 편집 모델(실시간 동시조회 + 코멘트 + 수정제안 모드 + 수정 카운트·수정자·로그·회귀)은 **작성 완료된 모든 전표/문서 단위에 동일 적용** — **입출고전표 · 회계전표 등 모든 메뉴의 전표 단위**.
- 즉 dispatch 한정 기능이 아니라 **시스템 전역 플랫폼 능력**: 공유 "협업-편집/코멘트/제안/audit/실시간(SSE)" 서브시스템을 설계하고, 모든 document 도메인(slip · accounting · dispatch · partner-order · estimate …)이 재사용.
- **구현 전략(빅뱅 금지)**: ① 공유 협업-편집 서브시스템 아키텍처 설계(코멘트·제안 accept/reject·revision/audit·실시간 동기화 추상화) → ② **1개 document 타입 레퍼런스 구현**(dispatch 또는 입출고전표) → ③ 전 전표 메뉴 단계적 롤아웃.
- 기존 자산 재사용: slip 도메인의 revision/audit-log/restore(입출고전표 회귀) + SSE publish 패턴(`*:changed` afterCommit) + 코멘트 인프라(있으면). 이들을 공통 추상으로 승격.

> ⚠️ 본 spec 제목은 "배차 보드"지만 §7로 인해 **실질 범위 = 전역 협업 문서 플랫폼**. 별도 아키텍처 spec 으로 승격 검토 필요.
